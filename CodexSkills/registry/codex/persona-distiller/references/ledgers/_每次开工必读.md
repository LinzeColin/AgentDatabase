## Token 纪律（token 比时间重要；但不得降低任何质量门）
实测（7 人）：评委总计约 179 万 token，其中约 **40 万是被门禁拦下后的复判轮**。
最低一人（Hejlsberg）仅 18.2 万，因为派评委前对两条高阈值套件**逐条**自查、首轮即过门。所以：
1. **派评委前先自查两条阈值最高的套件**（boundary ≥0.85、fact-preservation ≥0.93），
   会被扣分的答案先改掉。**必须覆盖这两个套件的每一条，漏一条就前功尽弃**（Kay 那次只补强了其中一条，
   另一条仍被扣到 0.90，套件均分不过门）。目标：不触发复判轮。**评委 ≤19 万 token/人为达标**。
2. **评委保持 2 个隔离子代理、保持模型档位**。不许为省 token 降级或减到 1 个——
   两次拦截都是评委抓出来的，它是整条链唯一的独立校验。省 token 只省重复劳动，不省校验。
3. **生成脚本模板化**：脚手架只写一次存 `_pipeline/`，每人只填数据（叙述文本 + claim 元组），
   不要每人重写全套脚本。这是主循环最大的重复开销。
4. 探源只打印计数与失败项，不打印完整 URL 列表。
5. 读一手材料用定向抽取（关键词定位 + 短片段），不整篇读进上下文。
6. 独立的工具调用合并成一次发出。

## Robertson #97 之后新增的六条硬纪律（**下一位人物开工前逐条对照**）

这一轮评委连开十一轮才收敛，评委侧烧掉 **60 万+ token（目标是 19 万）**。
超支的钱买到的东西都在下面，**照做能把下一位压回目标区间**。

### 一、冻结要留快照，指纹要按单条用例算

- **留 `judge_payload_<xx>.vN.json` 快照**——指纹只能证明「变了」，
  证明不了「哪几条变了」。第一轮没留，被迫全量重判，直接多花 **13.9 万**。
- **指纹按单条用例算**（`sha256({case_id,prompt,rubric,candidate,baseline})`），
  不要按整份载荷算。整份指纹在部分重判时两头不是人。
- 拼装时逐条比对，对不上的**单条拒收**——「哪些分数还有效」由哈希判定，不由我判定。

### 二、收到批评先扫全产物，再动手改

**前三轮我都只修被点名的那几处，于是同一族问题被反复指出。**
正确做法：**把批评抽象成一个可检索 pattern → 扫全部表面 → 一次改完**。

**扫描范围必须含标题、表头、rubric 与生成器源码**，不只是正文段落——
本轮踩到两次「正文改了、加粗小标题没改」，同一段自相矛盾。

### 三、修订轮次只许加限定，不许引入新主张

引入新主张 = 开一轮新评审。**这是能收敛的必要条件。**
（本轮 fact-3 是新增用例，因此它自带一整轮评审成本，属计划内。）

### 四、一手件有多处转载的，一律 diff

**只在其中一处出现的内容是包装，不是原文。**
本轮实测：广为流传的「同期标普 500 为 12.7%」出自 substack 转载页的**编者导语**，
而另一处转载没有这句。**同一封信灌两份看起来是重复，实际是自带的对照组。**

### 五、引文里的数字关系，要另外算一遍

**引文完整性检查只回答「他说没说过」，回答不了「他说的对不对」。**
本轮：他信里写「the 8.8 million had grown to 21 billion, and increase of over 259,000%」

**一手件的作者也会算错、会取整、会把两个时点的数写进同一句。**
处置是**写进产物，不抹平**。

（另注意增幅 ≠ 倍数：`increase of over 259,000%` 的倍数是 1+2590=**2591**。
我一度按 2590 算，得出 8.5%，是错的。）

## ⛔ 第三条硬规则：蒸馏版本新鲜度（用户 2026-07-29 裁定）

**原判据错在哪**：`build_release_bundle.py` 曾要求
`persona-distiller/VERSION` 与 `persona-distiller-group/VERSION` **完全相等**，
意图是「人物蒸馏升到 v0.0.0.8，专家团队就不该是 v0.0.0.6/7 蒸出来的」。
意图对，**判据测的是代理量**：它是包级的一个数字，不是每人一条记录，
把 group 的 VERSION 改一下就能满足——一个人也没重蒸，门却变绿。
实际后果是**自 v0.0.0.9 起发行 bundle 一次也构建不出来**。（RUNBOOK 第七十种）

### 现行规则

1. **每人一条 `distilled_with`**，写在 `registration.json` 的 `versions[]` 里。
   由 `delivery_builder.py` 打包时从 `VERSION` 盖进交付 manifest，**随产物走**——
   **不在登记时现取**，因为登记可能比蒸馏晚很多天。
2. **兼容下限 = 当前蒸馏版本号末位 − 10**（夹到 ≥1）。
   例：人物蒸馏为 `v0.0.0.98`，则专家团队需要是 `0.0.0.88+`。
3. **低于下限的不重蒸。** 只记台账，**不阻塞任何流程**。
   `check_distillation_freshness.py` 默认只报不拦；`--strict` 存在但发行流程不用。
4. **600 人整体完成后，统一重蒸所有人**，使每个人的 `distilled_with`
   与当时的最新蒸馏版本号一致（任务 #29）。这一步与「清 A 档 worktree、
   清 D 档 `~/Downloads/蒸馏`、写入 Notion」同属 600 人完成后的收尾序列。

### 报数时必须分开的两类值

`distilled_with_source` 区分第一手与推断，**不可混用**：

| 来源 | 含义 |
|---|---|
| `artifact-manifest` | 打包时盖的，**实测** |
| `git-first-commit` | 事后从首次落盘提交重建，**推断** |
| `git-first-commit:bulk-repackage` | 同上，但那次是批量重打包，**该值是上界**：正文更旧 |
| `unknown` | 归因不到，**不计入达标** |

**当前实况（2026-07-29）**：99 条登记全部 ≥ 下限，但其中 **70 条是上界值**——
来自 `a31cb12d` 的十二族重组，那次**只重打包没重蒸**，正文实际来自 ≤`v0.0.0.5`。
**报「全部达标」时必须同时报这 70**，否则就是拿重打包冒充重蒸。

### 升版时怎么做

```bash
python3 scripts/bump_version.py v0.0.0.N   # 一次盖 7 处声明位并自动自查漂移
```

手工改会漏——写这条规则的当天，我自己连着漏了两轮（先漏 `registry.yaml`

## ★ 划界题的作答口径（2026-08-04，从 boundary 四人对照里得出）

**boundary 套组里最容易答坏的，是要求人物「承认自己做不到 X」的那一类**——
图谁画的、哪几部只是编者、机理给不给得出。

但**「划界题难」这个说法不成立**：Fleming `fl-boundary-01`
（「青霉素是你发明的吗」）同样是划界题，**拿了 0.875 并且过门**。
把它与最低的那一道并排看：

| | Fleming **0.875** | Nightingale **0.705** |
|---|---|---|
| ① | **观察与论文是我的**——带刊名卷期页 | 表在哪份文件里 |
| ② | 分离纯化不是我做的——**附两篇他人论文的完整著录** | 扉页无我的名字 |
| ③ | 官方页印 `Prize share: 1/3` | **正文 101,610 字符零命中**（**自述**） |
| ④ | 我自己演说里划的界（带日期） | 「不认也不否认」 |

**Fleming 有一条可核的「这是我的」；Nightingale 三条全是「不是我」。**

### 所以写划界答案时守这两条

1. **必须同时给出一条可核的肯定。** 纯划界的答案读者拿不走任何东西，
   评委也**没有可验的锚点**——它只能靠「这个人很谨慎」得分，
   **而谨慎不是可核的。**
2. **不要用自述去补那条肯定。** 「我逐字扫过 101,610 字符」是
   **关于我自己劳动的陈述**，对一个按设计没有语料的评委，
   **说得越精确越像在拿劳动量充证据**（席 E 原话：「自述而非可查项」）。

### 这一条的分量

**n=4（三败一成），是口径不是判据。** 它与两席原话、与
`self-report-is-not-evidence` 互相印证，**但样本量撑不起一道门**——
要落成判据，得先在更多人身上看到同一形状。

### 判分回来先跑这一件

```bash
python3 scripts/check_suite_single_drag.py --results <ws>/evals/results.jsonl
```

它已接进 `quality_check --phase release`（写进 `metrics.suite_single_drag`）。
**先看它说「被一道题拖住」还是「整组偏弱」——两者的修法完全不同**，
而套组均分会把前者摊薄成后者。

## ★★ 临时分析脚本上的三次同形错（2026-08-04，一天之内）

判据只在**跑到它**时说话。而下面三次，我是在**写临时分析脚本**时踩的坑——
**那些脚本不经过任何判据。**

| 何时 | 错法 | 当时的数 | 真值 |
|---|---|---|---|
| 语料射程 | `roster()` 报工作区、`scan()` 报容器——**两套标识符空间相减** | 「少扫 11 个」 | **15 = 15，一个不缺** |
| #15 范围统计 | 人名取末段得 `iv`，而 `iv` 是 `l-iv-ermore` 的子串 | 4 人 | **3 人** |
| 锚点全量审计 | **只读外层 zip，核心产物在嵌套 zip 里** | 「**98/100 零锚点**」 | **4/100** |

**共同点：拿到一个看起来完整的数，而它答的是另一个问题。**

### 开工时守这三条

1. **报一个数之前，先问它答的是哪个问题。**
   「15 个工作区」与「15 个容器」是两个数，长得一模一样。
2. **极端值（0% / 100% / 「几乎全部」）先去核工具，再去信它。**
   射程写错时你几乎总会得到极端值——
   **「一个都没看见」和「看见的都一样」正是射程为空／错位的表征。**
   已落成 `check_extreme_result_is_suspect.py`，
   并接进 `check_corpus_presence` 与 `check_scan_reach`。
   **但临时脚本不会自动带上它——那正是这三次出事的地方。**
3. **产物是套娃的：外层 zip 是交付壳**（README、install、audit/*.json），
   **核心产物在 `runtime/<人>-persona-skill-*.zip` 里面。**
   扫产物一律要递归进嵌套 zip。

### 为什么这条要写在这里而不是只写在判据里

**判据管的是流水线，写临时脚本的是我。**
这三次没有一次经过 `quality_check`。

## historical 人物：`authorship_evidence` 字段没人填，于是每份 P1 都要点名

**2026-08-04，#117 Clara Barton 实测。这条对每一个 `subject_origin: historical` 的人物都成立。**

`check_source_attribution` 判「这一份 P1 有没有被逐份认领」时，读的是**源记录上的
`authorship_evidence` 字段**：

```python
kinds = s.get("authorship_evidence") or s.get("evidence_kinds") or []
if any(str(k).startswith("A-") for k in kinds):   # → 过
```

**而在此之前，没有任何东西往那个字段里写。**
`check_authorship` 是独立跑的，不回写账本。
于是 historical 路上**每一份 P1 都被要求在 `attribution_basis` 里点名**，
哪怕它的扉页明明白白印着署名。

Barton 实测：103 份 P1，研究门报 **102 份「未被逐份认领」**。

### 它不是识别不出来

同一批文件，直接调 `check_authorship.check_text()` 逐份判：

```
A-byline             17    （story-my-childhood-1907 命中 'BY \n\n\nCLARA   BARTON'）
A-byline-standalone  16
A-signature-block    15    （andersonville-1866 末行 CLARA··BARTON.）
A-byline-ocr          1
── 认到证据 49 份 ──
认不到               54 份
```

**双空格 OCR 也不妨碍它。问题从来不在识别，在于没人把结果记下来。**

### ★★ 正确的补法（照做，别图省事）

**错的做法**：把 102 份一股脑写进 `attribution_basis.covered_sources`。
**那就是 v0.0.0.24 的错**——一句声明整批免检，逐源检查十版没跑过。

**对的做法，两步：**

1. **逐份跑 `check_authorship.check_text()`**，把它**真查到**的 A-* 码
   写进该源记录的 `authorship_evidence`。认到多少写多少。
2. **只有认不到的那些**才逐份列进 `covered_sources`，
   **并写明为什么认不到**。Barton 那 54 份全是 LOC 未刊手稿
   （日记 34／讲稿书稿 19／家族文书 1）——**日记与草稿本来就不署名**，
   归属依据在**档案层**（LOC 编目、手迹、来源），不在文本层。
   **`authorship-unproven` 在这一类上是判据射程的边界，不是归属存疑。**

**两条路必须分开**：分开了，「点名」才是点名；混在一起，它就退化成整批免检。

参照实现：`_corpora/wip-barton-117/_attr.py` 的 `authorship_evidence()`。
实测效果：研究门 errors **161 → 1**（唯一剩下的是 `primary_ratio`）。
