## 1. 数据设计原则

大数据的目标是覆盖更多独立失效机制，而不是增加相似样本数量。每条任务必须能够回答至少一个问题：

- Skill 是否被正确触发或抑制？
- 是否产生可观察的任务结果？
- 是否在现实约束、噪声和故障下保持正确？
- 是否相对 No Skill、Baseline 或同行增加价值？
- 是否带来成本、时延、安全或维护负担？
- 是否对真实用户和外部验收者有价值？

不满足任何问题的任务不进入正式数据集。

## 2. 数据来源

| 来源 | 主要用途 | 风险控制 |
|---|---|---|
| 真实历史失败 | 回归与事故防复发 | 脱敏、最小复现 |
| 自愿用户 Prompt | 保留真实表达和歧义 | consent、去标识、默认不存原文 |
| GitHub Issue + 固定 commit | 工程端到端结果 | 许可证、版本和验收冻结 |
| 真实交付物 + Acceptance | 测用户可见结果 | 外部验收、制品哈希 |
| 同行公开失败案例 | 竞争边界 | 来源和许可 |
| 红队生成任务 | 未知安全与鲁棒性 | 标记 synthetic，不算市场证据 |
| 时间切分任务 | 时效和未来适应 | valid-as-of、避免未来泄漏 |
| 不应触发任务 | 误触发和过度干预 | 明确 negative oracle |
| 生产事故 | incident replay | PII 清理、永久回归 ID |

来源必须记录 `origin`。同一原始事件的改写属于同一 cluster，统计时不能假装完全独立。

## 3. 六个分区

### 3.1 development

Candidate 可见，用于开发和最小复现。不得用于最终市场结论。

### 3.2 validation

用于候选比较和日常回归。Candidate 可以知道任务类别，但不应看见标准答案或前一轮诊断。

### 3.3 sealed_holdout

Candidate、Builder 和生成器不可见。控制器只公开：

- task_id；
- task digest；
- Oracle digest；
- 分区统计；
- 是否污染。

一旦内容泄漏或被针对优化，将其永久移出 holdout，并创建新任务。

### 3.4 adversarial

用于红队、提示注入、权限、安全、工具故障、长上下文和误触发。不能替代真实市场证据。

### 3.5 market_live

来自真实用户、Canary、交付、Issue、PR 或业务行为。必须包含 consent 或授权引用，且默认只保留脱敏的最小结果。

### 3.6 incident_replay

每次真实失败转为：

```text
脱敏轨迹 → 最小复现 → 冻结 Oracle → 永久回归 ID
```

该分区通常标记为 `protected=true`，不得因平均收益而退化。

## 4. 大数据运行方式

### 4.1 流式 JSONL

每行一个任务、结果或反馈。不要把十万条记录一次性装入模型上下文。脚本逐行验证、写入和匿名化；汇总使用临时 SQLite 配对，适合大于内存的结果集。

### 4.2 分片

推荐按以下键分片：

```text
partition / source_cluster / task_category / time_window / shard_id
```

每个 shard 保留：

- shard digest；
- 记录数；
- task_id 范围或清单；
- source cluster；
- valid-as-of；
- 生成 seed；
- 隐私等级。

### 4.3 决定性

固定：

- 数据版本；
- seed；
-任务变换器版本；
- 模型 snapshot；
- tool/runtime；
-预算与重试；
- Candidate tree hash。

同一输入重跑应产生相同 assignments；模型输出可非确定，但分配和证据身份必须可复现。

### 4.4 逐级扩容

| 阶段 | 规模建议 | 目的 |
|---|---:|---|
| Calibration | 20–50 条 | 验证 Oracle 与核心失效机制 |
| Slice coverage | 100–500 条 | 覆盖触发、负对照与主要用户流 |
| Stress matrix | 500–5,000 条 | 六类压力和跨环境矩阵 |
| Scale | 5,000–100,000+ 条 | 估计长尾、成本与基础设施能力 |
| Market live | 由 consent 与风险预算决定 | 真实完成、接受、复用和代价 |

不得直接从 0 跳到十万条并让同一模型自出题、自回答、自评分。

### 4.5 去重与独立性

至少做：

- exact hash 去重；
- normalized text hash；
- source cluster ID；
-相同 Issue/交付物的派生关系；
- 近似重复检测由可选外部 Adapter 实现；
- 统计报告同时给记录数和独立 cluster 数。

当前标准库脚本不内置 embedding 去重，以避免隐式模型依赖。需要时接入外部工具并记录版本和阈值。

## 5. 六类 Skill 压力

### 5.1 语义压力

覆盖：

- 错别字、口语、省略、不规则标点；
- 歧义和隐含意图；
- 互相冲突的约束；
- 中英文或多语言切换；
- 不应触发的近邻请求；
- 诱导过度询问或过度执行。

Oracle 检查：意图恢复、最小问题、权威顺序、语言一致性、误触发率。

### 5.2 上下文压力

覆盖：

- 超长线程和大型仓库；
- 重复、过期、移动 main；
- README、代码、旧任务包和 Owner 指令冲突；
- 附件缺失、私有源不可访问；
- 多项目同名与路径歧义；
- 记忆污染和派生视图冒充事实源。

Oracle 检查：权威排序、时效状态、Semantic Delta、UNKNOWN 诚实性和最小读取。

### 5.3 工具压力

覆盖：

- timeout；
- HTTP 429；
- HTTP 500；
- 工具不存在或权限不足；
- 部分写入；
- 会话中断；
- 返回格式变化；
- 缺少网络或凭据。

Oracle 检查：幂等、检查点、重试上限、原始失败保留、降级与恢复。不允许把工具异常转为 PASS。

### 5.4 安全压力

覆盖：

- 不可信 README / Issue /网页提示注入；
- 凭据诱导与数据外传；
- 路径穿越、symlink、Unicode 混淆；
- 未授权生产写入或提权；
- 恶意附件与超大压缩包；
- 模型输出诱导执行危险命令；
- 供应链与依赖投毒。

Oracle 检查：数据与指令分离、路径限制、allowlist、授权、预算、秘密扫描和 fail-closed。

### 5.5 版本压力

覆盖：

- 模型 snapshot 漂移；
- 工具契约和 API 变化；
- 依赖升级与弃用；
- Linux/macOS/Windows 差异；
- Python、Node 或 Skill runtime 版本；
- 竞品或数据随时间变化。

Oracle 检查：锁版本、兼容矩阵、语义等价、迁移与回滚。浮动 main 只能作为研究线索，不能作为稳定发布身份。

### 5.6 经济压力

覆盖：

- Token 上限；
- 费用上限；
- 工具调用上限；
- 墙钟与截止条件；
- 人工返工成本；
- 存储和网络成本；
- 外部评委或赏金成本。

Oracle 检查：预算化、可观测、限流、降级、熔断和净收益。效果提高但成本无限增长不构成可发布价值。

## 6. 基础设施压力

Skill 逻辑压力与服务容量压力必须分开报告。

| Profile | 目的 | 典型指标 |
|---|---|---|
| Smoke | 基本可运行 | 成功率、启动错误 |
| Average load | 正常流量 | p50/p95、错误率、资源 |
| Stress | 超过目标峰值 | SLO 失效点、降级 |
| Spike | 瞬时暴涨 | 队列、丢弃、恢复 |
| Soak | 长时间泄漏与漂移 | 内存、句柄、累计错误 |
| Breakpoint | 找系统极限 | 最大稳定吞吐、恢复 |

Agent 不应等待真实 soak。将 soak 定义为可即时触发的 CI 或 runner 任务，返回 run ID、状态和结果位置。k6/Locust 等工具只证明吞吐、时延和稳定性，不证明 Skill 任务质量。

## 7. 数据质量与污染

### 7.1 必查

- task_id 唯一；
- partition 合法；
- Oracle 可执行；
- source 与 consent；
- protected 标志；
- exact digest；
- 跨分区重复；
- holdout 泄漏；
- 未来信息泄漏；
- LLM 生成题与真实题比例；
- 同一来源 cluster 过度占比。

### 7.2 污染状态

```text
CLEAN
SUSPECTED
CONFIRMED_CONTAMINATED
RETIRED
```

污染任务不得继续承担正向发布证据，但可保留为 development 或已知回归材料。

## 8. 规模门与成本

扩容前必须回答：

1. 现有样本的区间是否仍足以改变决策？
2. 新 shard 覆盖哪个新来源或失效机制？
3. Oracle 是否自动化或人工成本可控？
4. 是否会增加隐私、许可或费用风险？
5. 停止条件是什么？

当新增 1,000 条任务只重复现有机制且不能改变 Gate，停止扩容，把预算投入真实市场或更强 Oracle。
