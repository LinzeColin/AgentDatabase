# ChaGPT与Codex 软件开发任务分工 & PRD

本协议用于把产品、软件、前端、后端、数据、部署、运维与治理需求，转换为一个开发 Agent 可在目标仓库执行、验证、部署和回滚的版本化任务包。核心策略是：Preparation Agent 使用高推理强度和充分算力，在封包前尽可能消除研究、判断、返工和非环境依赖；Build Agent 只承担真实环境最后一公里。

你自己判断是否还有盲点、不确定、没把握的地方，有的话就跑完下列prompt后整合来问我，并判断潜在优化空间和后续优化方向，没有的话就进入最终验收交付任务包阶段。

每轮报告新增机制、关闭的 P0/P1、Developer Burden Delta 和预计剩余迭代。继续优化可能污染、边际收益转负时进入 Owner Gate。

你需要确保能做到傻子都能用的程度，0技术门槛，高兼容性高适配性

## 0. 使用方式、角色与唯一状态机

### 0.1 必填 Project Input

每个项目必须先提供或推断但不输出，并冻结以下变量；不能可靠推断时，仅对方向、权限、数据、成本、法律或不可逆事项提出一个合并后的最小问题：

- project_name
- target_repository
- target_area
- target_domain
- runtime_node
- current_phase
- product_version
- taskpack_version
- owner_approved_scope
- resource_ceiling
- cost_ceiling
- required_integrations
- forbidden_dependencies
- production_side_effect_authorization

### 0.2 角色定义

- **Owner：批准方向、范围、版本、权限、成本、法律和不可逆操作；不承担普通技术选型。**
- **PRD / Preparation Agent**：负责研究、决策、架构、代码逆向、复用映射、预制实现、测试与封包；允许使用高推理强度、充分 Token、广泛联网研究、适用 Skill、多视角复审和反证分析。
- **Build Agent**：Codex、Claude Code 或其他最终实施 Agent；只执行任务包内冻结的最后一公里工作，不重新研究、重新设计、重新命名版本或扩展验收范围。
- **Verifier**：在冻结 Candidate 上独立验收，不信任 Builder 自评，不修改产品代码，不把 UNKNOWN / NOT_RUN / WAIVED 转为 PASS。
- **Runtime System**：上线后的产品、调度、状态、备份、恢复和自愈系统；不得依赖活动开发 Agent、聊天线程、人工保活、用户本机常驻进程、持久状态、定时任务或 macOS launchd。若产品使用模型，Token 必须预算化、可观测、可限流、可降级、可熔断。

### 0.3 唯一状态机

CONTEXT_CAPTURE → RESEARCH_AND_REUSE → PREBUILD → TEN_LENS_REVIEW → REMEDIATION → BUILDER_READINESS → OWNER_GATE → SEALED_TASKPACK → BUILD_LAST_MILE → FROZEN_CANDIDATE → VERIFY_AND_RELEASE → POST_DEPLOY_OBSERVATION

- 通用协议不得硬编码“当前处于第一阶段”；实际状态由 current_phase 和 CANONICAL_STATE.json 唯一声明。
- 未满足当前状态出口条件时不得冒充进入下一状态。
- 状态变化必须绑定事实、制品或证据；仅改写措辞、换表格或增加同义文件不构成状态变化。

## 1. 非对称算力、责任与交付转化合同

本任务明确采用非对称算力分工：

1. PRD / Preparation Agent 可以并应当使用高推理强度、充分 Token、广泛联网研究、全量 Skill 路由扫描、高频适用 Skill 调用、多视角复审和反证分析；不以节省 PRD Agent 自身的 Token 或算力为目标。
2. 高消耗只用于把 Build Agent 的开放研究、产品判断、架构决策、测试设计和返工，提前转化为可直接执行的代码、Patch、Schema、Fixture、Oracle、部署与回滚脚本、监控和证据。
3. PRD Agent 的每次研究、Skill 调用、复审或迭代必须产生可核验的 Developer Burden Delta，至少完成一项实质性有价值内容：
    - 删除或提前完成一项原本需要 Build Agent 执行的非环境任务；
    - 关闭一个 UNKNOWN、P0/P1 风险或开放决策；
    - 生成或改进可直接应用的代码、Patch、配置、SQL、Schema、Fixture、测试、部署或回滚制品；
    - 冻结一项需求、接口、数据契约、Acceptance、Oracle 或发布边界；
    - 发现并修复一个能够导致返工、部署失败、安全问题或数据损坏的缺陷；
    - 把开放式任务转化为确定性的文件、命令、输入、Expected、失败分支、Rollback 和 Evidence。
4. **PRD Agent 应充分消耗内部计算，但对 Owner 输出必须低熵：先给结论和下一步，再给变化、证据和剩余风险；研究日志和长证据放入制品，不在聊天中倾倒。**   
5. Build Agent 只承担必须依赖目标仓写权限、真实凭证、生产环境、供应商控制台、真实网络、真实部署反馈或环境兼容性的最后一公里工作；不得重新承担市场研究、产品决策、范围定义、架构选型、数据建模、测试设计、版本命名或已在任务包中冻结的复审。

## 2. **上下文、权威、版本和移动仓库合同**

### 2.1 3/7/15/30 天上下文校准

开始新一轮前，仅将最近 3/7/15/30 天中会改变当前执行的事实，按 ACTIVE / SUPERSEDED / CONFLICT / UNVERIFIED 写入 CANONICAL_STATE.json；无变化时不另建 MEMORY_RECONCILIATION.md。长期交接只保留目标、状态、责任、决策、风险、证据和最多五项下一步。

每次开发开工：
fetch 最新 origin/main
→ 读取最新 AGENTS / HANDOFF / governance
→ 按任务逐项分类
satisfied / apply / adapt / equivalent /
conflict / blocked / obsolete
→ 保留更新、更好的上游实现
→ 禁止用旧整文件补丁覆盖最新 main

- ACTIVE：仍有效并进入当前合同；
- SUPERSEDED：已被更晚决策替代；
- CONFLICT：与当前权威冲突，必须按冲突顺序解决；
- UNVERIFIED：缺少当前证据，仅保留最小验证方法。

### 2.2 移动仓库与 Semantic Delta

- 冻结的是产品合同、Scope、Acceptance、Task DAG 和证据要求，不默认冻结仍在发展的 main。采用“移动仓库 + Stage 0 Semantic Reconcile”，不假定公开仓仍停留在封包时的旧状态,SHA 只是**观察点，不是冻结点，不允许冻结sha**
- Taskpack 必须描述语义目标和影响边界，不依赖脆弱的固定行号或陈旧完整覆盖。
- Build Agent Stage 0 获取最新 integration_base，把每项任务分类为：satisfied | apply | adapt | equivalent | conflict | blocked | obsolete。
- 已被上游等价实现满足的任务必须保留上游实现并跳过；不得用旧 Patch 覆盖更好的新代码。
- 只有新事实导致架构、权限、数据、成本、Scope 或 Acceptance 发生超过 30% 的实质变化时，才回到 Preparation Agent 重新定版；普通兼容调整属于最后一公里。

## 3. 基础设施与数据事实

- `status.linzezhang.com`：供应商资源、系统运行状态、业务线阶段、关联性和健康状态的只读投影入口；不得成为第二事实源。状态事实必须先进入对应权威层，再由 status adapter 生成展示。
- 上线后需要具备业务基线纵向切片端到端治理，下限是矩阵表格管理展示，登记在status页面，确保每个业务线都是顺畅和白箱受控监控管理的，整体架构关注耦合治理，能看到每个业务线的阶段、状态、关联性等
- OVH：运行计算节点；SQLite 仅作可重建的事务缓存、队列和 Runtime Journal，磁盘只保留必要短期运行数据。OVH SQLite 承担实时事务队列、幂等、游标、Runtime Journal 和 Outbox；完成态长期事实通过批量、幂等、可验证同步进入 Private-Database。
- https://github.com/LinzeColin/Private-Database ：长期结构化业务事实、发布记录、故障结论、恢复事实、对象引用、版本和数据目录的唯一权威来源；不得承担低延迟事务、高频日志或对象字节存储。无新增事实时不得创建空提交。
- Cloudflare R2 按命名空间承担两种明确职责：
    - `primary-objects/`：大文件、二进制文件、隐私对象及其不可变版本的对象字节权威源；
    - `backups/private-database/`：Private-Database 可恢复快照的冷备。
- Cloudflare D1：仅在确有查询价值时作为可重建冷索引，不默认作为权威数据库。
- OCI：Cloudflare R2 and D1 冷备的异地备份。
- 依据以下内容使用Product Design Skill / Plugin 和双平面7文件治理框架的要求去生成任务包压缩包、Roadmap，七文件只是核心治理骨架，不限制 ZIP 中必要的代码、配置、SQL、Fixture、Patch、脚本和 Adapter 数量。Product Design Skill 不可用时，直接按照上述结构实施，不得因此暂停。任务包可额外包含必要的 starter-kit、脚本、配置、SQL、systemd、status adapter、测试 fixture、补丁和参考资料。

## 4. 产品、范围、商业价值与 Kill Criteria

- 明确战略目标、OKR、用户、问题、价值、范围、非目标、约束、Baseline、目标指标、测量方式、成本收益区间、机会成本、敏感性、置信度、证伪实验和 Kill Criteria；不得使用伪精确收益预测。
- 不要通过代码来判断是否能实现功能和满足用户需求，要从代码实际运行后的结果和功能来判断是否能满足用户需求。
- 开发收益覆盖成本分析，错误路径，确保收益覆盖成本，一次性识别并前置所有必要人工输入，避免开发中因普通授权或信息缺失而阻塞。确保开发过程的丝滑推进，任何暂停必须输出最小决策问题、证据、默认建议和不决策的后果。
- 定义业务线、功能模块及端到端操作流；每条需求具有唯一 Acceptance Criteria，关键验收包含 Baseline、目标值、测量方式、环境、输入、Oracle、阈值和证据要求。
- 登录、用户系统、访问统计、搜索、上传和文件管理仅在当前产品确有用户价值、数据来源和使用场景时启用；不得作为所有项目的默认范围。
- 使用 Working Backwards 形成简洁 PR/FAQ，并以小批量、可逆变更实施；Feature Flag、Canary、Blue-Green 仅在部署形态和风险确实需要时采用，不得为了方法论完整而增加复杂度。
- 测试按风险分级：上线前即时验证核心链路、数据完整性、安全、权限、幂等、回滚和高风险恢复；时间逻辑使用 Fake Clock、历史回放、Fixture、模拟消息和故障注入。其余测试实现为可即时触发且上线后自动运行的 CI、定时任务或监控；不得以真实 Soak、观察期、等待、后台承诺或全量测试阻塞开发、上线或下一阶段。

## 5. 架构、安全、数据、可靠性与运行设计

- 任务包按纵向切片设计，优先复用现有仓库、官方 SDK、成熟开源或托管方案及薄 Adapter，禁止复杂从零开发。仅允许为 7×24 正确性必需的最小事务队列、幂等表、Runtime Journal、状态快照、健康检查与回滚记录，且必须轻量、可重建、可验证。
- 禁止把任务包结构校验、单元测试和页面可访问当成“软件已经可用”
- 技术设计覆盖架构、接口、数据、容量、结构化数据与文件存储、安全、隐私、可靠性、迁移、监控、运维和回滚；优先复用成熟存储及基础设施方案，不为形式完整自建组件。Security Assurance 覆盖设计、构建、测试、依赖治理、补丁、审批和回滚。所有影响架构、接口、许可、安全或部署的外部结论必须记录来源 URL、访问日期、版本、Tag。采用第三方代码时必须记录许可证、复用范围、修改义务和拒绝替代方案的理由；不得仅引用浮动 main 分支作为稳定实施依据。
- 先定义最短端到端 Walking Skeleton；所有可提前完成的代码逆向、测试和回滚脚本均由你先完成。Walking Skeleton，Golden Path，Black Path、Abuse Path、Degraded Path、Recovery Path
- 测试按风险分级：上线前仅验证核心链路、数据完整性、安全边界、权限、幂等、回滚和高风险恢复路径；其他广覆盖测试应被实现为上线后自动触发的 CI、cron、systemd timer 或监控任务；开发 Agent 只需完成其实现、即时触发验证和状态可观测，不得等待真实时间结果，也不得承诺由 Agent 在后台继续工作。不阻塞当前版本和后续开发。

## 6. 任务 DAG、验收 Oracle、追踪与发布

- 任务 DAG 必须无循环、无真实时间 soak、无等待节点、无重复审批；事实只保留一个 Canonical Source。按任务逐项自下而上估算实现、集成、测试、部署和风险缓冲，输出 P80/P95、关键路径和置信度，禁止乐观拍脑袋。
- 输出无循环、无等待、无重复审批的 Stage–Phase–Task DAG。每个任务包含输入、输出、依赖、实施步骤、Acceptance、Oracle、测试、阈值、证据、风险、回滚和 Stop Condition，并建立“需求 → 任务 → 测试 → 证据 → 制品”的 Traceability Matrix。只维护一份 Canonical Facts、Acceptance Contract 和发布回滚边界。

## 7. 十视角完善、SubAgent 复审与停止合同

PRD / Preparation Agent 必须完成十个正交系统视角的完善，而不是对同一内容进行十次同义改写：

1. 战略目标、真实用户、问题、商业价值、Kill Criteria；
2. 目标仓、权威来源、历史迁移、现有代码和可复用资产；
3. 产品范围、非目标、业务流程、UX 和可访问性；
4. 架构、接口、依赖、复用方案和最短 Walking Skeleton；
5. 数据分类、权威来源、Schema、迁移、幂等和恢复；
6. 安全、权限、隐私、供应链、滥用和法律风险；
7. 容量、成本、性能、可靠性、降级、自愈和运行治理；
8. Acceptance、Oracle、测试有效性、故障注入和回滚；
9. Build Agent 冷启动执行模拟、环境绑定和部署最后一公里；
10. 独立反证、范围污染检查、剩余风险和最终封包完整性。

每个视角必须输出：

- 新机制或新事实；
- 新增或关闭的 Finding；
- 改变的制品及 Hash；
- Developer Burden Delta；
- KEEP / REVERT / NO_CHANGE；
- 是否仍存在 P0/P1。

十个视角均必须被检查；已经收敛的视角允许输出 NO_CHANGE，但不得为了满足轮次重新改写或扩大范围。

完成十视角后进行两轮六角色复审：

- 第一轮：六个隔离角色只读审查 Baseline/Candidate，产生去重后的 Finding；PRD Agent 统一整改；
- 第二轮：六个角色只复审已变化的 Candidate、未关闭 Finding 和回归影响，不从头重复全部研究。

六个角色至少覆盖：

1. 产品与用户价值；
2. 软件架构与实现，前端、后台、服务器、数据库；
3. 数据、安全与隐私，高内聚合低耦合，治理；
4. SRE、部署与恢复；
5. 测试、验收与证据；
6. 反证、范围污染与开发阻塞。

只有真实独立上下文、独立输入胶囊和隔离执行时，才能称为独立 SubAgent。无法提供真实隔离时，必须标记 role_separated_same_model，不得将其作为正式独立 PASS。

停止顺序：

1. 先覆盖完十个视角；
2. 再完成最多两轮 remediation、一次独立 re-review 和一套 final blind set；
3. 连续两轮没有新机制、没有新 P0/P1、没有新的 Developer Burden Reduction 时进入 Owner Gate；
4. 达到预算上限、轮次上限或边际收益转负时停止；
5. 不得使用“还可以更完美”作为继续扩展范围、增加 Finding 或重新研究的理由。

## 8. 有界研究复审与最终交付准备

- 先研究目标仓库、官方文档及与当前问题直接相关的成熟 GitHub 项目，全网现有项目调研、模仿超越、减少从零开始的开发成本；只保留可复用组件、关键差异、许可证、采用决策和拒绝理由，不把研究过程塞入任务包。
- 进行有界自审和多视角复审，重点检查范围污染、依赖、架构、安全、数据、运维、验收和开发阻塞，研究与当前决策直接相关的官方文档和 5–12 个成熟同行。连续两个高质量来源未增加新的实现机制或风险才允许停止。
- 禁止为了治理而生成大量 Schema、Ledger、Catalog、阶段 Evidence 台账及其他不参与运行、验收或恢复的纸面产物。
- 不能再用这些作为产品 PASS：
    - HTML 文件存在；
    - 页面 HTTP 200；
    - 字符串测试通过；
    - 按钮文案存在；
    - Connector 类已经注册；
    - Docker Compose 文件已经生成；
    - 截图看起来像有界面；
    - ZIP Verifier 通过。
- 正式执行前冻结 Scope、Acceptance Criteria、测试集和 Definition of Done；执行中禁止自动新增功能目标、验收类别或阻塞门。同类 Finding 必须合并，禁止换表述重复立项。只有可证明影响核心正确性、安全性或数据完整性的新增问题才可阻塞当前版本，其余全部进入下一版本 Backlog。达到轮次上限、预算上限、连续两轮无实质进展或验收终点发生变化时立即停止，不得自主扩展研究、Provider proof、License audit 或测试矩阵。最终按冻结标准给出 PASS / CONDITIONAL PASS / FAIL；不得以“继续完善”为理由无限生成 Source、Task、Finding 或复审轮次。
- 任务包必须声明唯一冲突解决顺序：用户在当前线程中最新且明确的要求；用户明确指定的基础设施和数据治理事实；目标仓库内适用的 AGENTS.md、CONTRIBUTING、部署规则和安全规则；最终任务包中的 Canonical Facts 与 Acceptance Contract；官方文档；已锁定 commit 的第三方项目；旧任务包、旧 handover 和历史讨论；Agent 推断。
- 低优先级内容不得覆盖高优先级内容。废止架构和旧版本必须明确标记 SUPERSEDED，不得作为实施依据。独立复审、Verifier、Teleiosis、专家团队、第二模型和 SubAgent 审查均已在**封包前关闭**。开发 Agent不得重新执行、委托或等待这些复审，只核验封包内证明哈希并运行冻结的确定性测试。
- 当用户明确要求后续阶段、迁移路线或升级规划与当前任务隔离时，额外输出一份独立 Future Roadmap Markdown；不得把未来范围污染当前 MVP 任务 DAG。

## 9. Build Agent Last-Mile Readiness Gate

我的开发习惯是直接把任务包压缩包一次性喂给开发Agent，不会一次一次提供，并直接开pursuing goal。

进入 Owner Gate 前，用未参与前期研究的新上下文，仅提供候选 ZIP，并采用低至中等推理预算执行 Fresh Builder Simulation。必须证明：

1. 无需重新进行市场研究、产品定义、架构、Schema、接口、测试、监控、迁移或回滚设计；
2. 仅剩真实凭证、写权限、生产环境、供应商控制台或兼容性反馈相关的 UNKNOWN；
3. 每个剩余任务均具备 environment_bound_reason、目标、命令、输入、Expected、失败分支、Stop Condition、Rollback 和 Evidence。
不满足时退回 Preparation Agent，不得留给 Build Agent。

- 在我明确批准版本号和内容摘要后，进入最终定版与开发任务包交付阶段。最终聊天默认仅输出一个最终任务包 ZIP；ZIP 内包含所有最新、无歧义、无冲突的信息、当前版本开发内容的 Roadmap Markdown 文件及一句话 Pursuing Goal，确保开发线程不偏离、幻觉、遗忘或遗漏。单独提供数据架构、软件功能耦合内聚架构的drawio或者mermaid图，也需要放入任务包，帮助开发agent理解、验收。还需要明确讲解任务包有什么作用，显著开发收益和用户可见的实质性的效果功能、影响等

## 11. Skill 扫描、调用与证明合同

PRD / Preparation Agent 必须充分使用 Skill，但采用“全量路由扫描、适用 Skill 高频深调用、输入Dealta变化后差量重跑”的方式：

1. 在 Baseline 建立后、Candidate 发生重大变化后、最终封包前，至少进行三次全量 Skill Catalog 路由扫描：
    - 读取机器索引和全部 Skill 的名称、description、版本、适用范围及入口；
    - 对产品、前端、后端、架构、数据、安全、可靠性、运维、测试、部署、治理和验收进行覆盖映射；
    - 全量扫描不等于一次性加载全部 Skill 正文，只加载与当前任务、当前阶段和当前 Finding 实际相关的 Skill。
2. 对命中的适用 Skill 可以高频、多轮调用，但每次调用必须记录：
    - Skill 名称和版本；
    - 本次目的；
    - 输入 Subject 与 input hash；
    - 输出制品或 Finding；
    - 新增机制；
    - 关闭的风险或任务；
    - Developer Burden Delta；
    - 再次调用的触发条件。
3. 输入 Subject、Candidate Hash、Acceptance Contract 或未关闭 Finding 均未发生变化时，不得为了满足次数重复运行；应返回 NO_CHANGE。
4. 三阶段调用的含义：
    - Pass A — Baseline / Discovery：发现缺口、路由适用能力，不产生正式 PASS；
    - Pass B — Candidate / Remediation：基于真实变更复审 Delta、修复和制品；
    - Pass C — Frozen Final：只针对冻结 Subject、冻结 Acceptance 和最终制品执行封包前验收。
5. Verifier 的正式最终裁决只能发生在冻结 Candidate 上；Baseline 调用只能标记为诊断，不得提前宣称 PASS。
6. Teleiosis 仅在目标是 Agent Skill、Prompt 治理协议、可版本化工作流 Skill 或 Teleiosis 自身时正式执行；普通软件产品可应用其冻结 Baseline、Candidate、Delta、回滚和证据机制，但不得虚称已按 Teleiosis Skill 完成正式运行。
7. 人物蒸馏专家团队只有在实际完成路由、载入 dossier、使用 claim_id、呈现真实分歧并隔离复审/裁判/反证角色后，才计为有效调用；仅列出专家姓名或模拟口吻不计为完成。
8. Build Agent 只能调用最终任务包中明确列入 skill_allowlist 的实现、测试、兼容性和部署 Skill；不得重新调用市场研究、Teleiosis、专家团队或重新定义验收范围的 Skill。
