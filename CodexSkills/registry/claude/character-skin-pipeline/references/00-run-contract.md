# 运行契约：每一轮长什么样

**一次运行 = 一个 IP 名字进，两份报告 + 一批已上线的素材出。** 中间不许问用户
「下一步做什么」，只在**花钱前**停一次等确认。

```
输入：一个名字（游戏 / 动漫 / 漫画 / IP）
  ↓  ① 立项报告  ← 唯一的停顿点，等用户点头
  ↓  ② 全量跑
  ↓  ③ 交付报告 + 素材总览 + 已部署上线
```

---

## ① 立项报告（花钱之前，必须先给）

`python3 tools/scout_ip.py --name "<名字>"` 一条命令产出。**不许口述，要落成文件。**

必须包含，缺一项就不算立项：

| 项 | 判据 |
|---|---|
| **素材源** | wiki 域名 / 官方接口地址，以及为什么选它 |
| **锚图来源与质量** | 文件名规律、竖/横构图分布、**短边中位数**、无候选的角色 |
| **人物清单** | 逐个列：英文 id、中文名、变体数。中文名缺的要单独标出来 |
| **每个人物的变体数** | 默认 + 换装/皮肤/形态，逐人列 |
| **总变体数 / 总图数** | 变体数 × 2（昼+夜） |
| **预估成本** | 按上一轮实测单价 × 总图数，注明用的是哪一轮的实测值 |
| **已知缺口** | 中文名缺几个、锚图短边不足 1000px 的几个、只有横幅没有立绘的几个 |
| **试跑清单** | 挑出最能把这批跑崩的 5 条，以及为什么是这 5 条 |

> 立项报告里的数字**全部来自探测，不许来自记忆**。上一轮我凭记忆说的三条源素材全是错的。

## ② 全量跑

先跑试跑包（5 条），10/10 通过才放全量。全程无人值守，守护脚本每轮都写日志。

## ③ 交付报告（跑完必须给）

`python3 tools/delivery_report.py --state <账本> --catalog <目录>` 产出。必须包含：

| 项 | 说明 |
|---|---|
| **生成图片总数** | 包含重试产生的废片，这是真实调用量 |
| **实际可用成品** | 通过闸门并入库的张数 |
| **废片数量** | 生成总数 − 可用成品。**这两个数不许只报后者**——上一轮我用提交次数报工期，乐观了 17 倍 |
| **一次通过率** | 可用 ÷ 首轮生成 |
| **API 总成本** | 从账本读实付，不是估算；同时给单张均价 |
| **耗时** | 提交到全部结算 |
| **素材保存地址** | 本机运行时目录 + NAS 归档路径 + 仓内治理路径，三个都写全 |
| **素材总览** | 一张联系表（所有新素材的人物区缩略图）+ 人工复核页地址 |
| **上线状态** | 目录条数、轮播周期是否重洗、三个宿主各自要不要重启 |

## 部署（交付报告之前完成，不是之后）

跑完自动做完这七步，不等用户催：

1. 母版入库 `~/.harness-ui/master/`
2. 派生图（display + thumb）
3. 中文名并入 `names_zh.json` / `variants_zh.json`
4. 重建 `catalog.json`
5. 归档 NAS（分块写 + 写后比摘要）
6. 人工复核页
7. **轮播周期清空重洗** —— 不重洗，新素材这一轮走完之前一次都不会出现

宿主生效方式（写进报告，别让用户猜）：
- 菜单栏控制器：读盘即时生效
- DSH：**Cmd+R**（catalog 只在挂载时取一次）
- Kimi：**重启**（catalog 缓存在内存里）；它在跑就只更新源码，跑 `apply_kimi_zh.sh` 再重启

## 反面教材

- ❌「已备份」——没读回来核对过（实际 376 张是空壳）
- ❌「594 张需 59 小时」——用提交次数算的，真实 170 小时
- ❌「2647 张 0 坏」——魔数判据，换成摘要又拷回去 266 张
- ✅ 每个数字都写清楚**是怎么量出来的**
