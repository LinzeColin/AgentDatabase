## ★★ 铁规：任何实验都必须用角色库的人 + 挂 LoRA（2026-08-24 用户判违规）

**产物必须是现有 IP 角色库的人物。那么实验就必须在角色库的人身上做。**

我犯过：复刻实验为了对齐一张非原神的对标靶图，**没挂 LoRA，出的是虚拟人物**，
理由是「靶子不是原神角色」。**这个理由本身就错**——
在通用人物上得出的画风结论**不保证迁移到挂了 LoRA 的角色上**，
而 LoRA 恰恰是最可能改变画风的那个变量（它学的是它训练集的画风）。

> **判据**：实验图里那个人，能不能一眼认出是角色库里的谁？认不出 = 这个实验对产线无效。

### 为什么身份只能靠 LoRA —— 锚图这条路走不通

`06_模型与资产/04_锚图/` 有 1690 张，**但原神册 715 张里竖图 0 张**，
全是 1280×720 这类横图。竖版壁纸用不了。
`_取用/03_角色就绪矩阵.csv` 把锚图标成「损坏 24 / 不合规格 6」= **0 可用**，
说的就是这件事（不是文件坏了，是规格不对）。

**结论**：本地路线的身份保真 = **角色 LoRA + L 轴标志特征**，二者缺一不可。
- LoRA 给体态与脸
- **L 轴显式写标志配件**（红绳/云纹/角/铃/梅花瞳…）——
  LoRA 学的是整体画风与体态，**标志配件最容易被构图/服装词冲掉**
- IP-Adapter **已证伪，别再试** —— 机理与实测证据见 `references/ipadapter-why-it-fails.md`
  （两种失败模式：全图生效与 ConditioningSetArea 打架长出第二个人物 / 锚图平涂风格污染。
  **是作用域问题不是强度问题，降权重无效**）

**这两件事我混过一次，代价是半天白调画风。**

| 级别 | 判什么 | 判据来源 |
|---|---|---|
| **一级 · 产线可用** | 参数跑得通、出得来图、不崩 | 自己实测 |

**过了一级不等于过二级。** 一张画质极好但尺寸/背景/成组结构不对的图，**下游用不了，进不了库。**

## ★★★ 验收先数，再看 —— 观感不是判据（2026-08-24 用户判死）

用户原话：「你这**全部都是四根手指**，我和你说了很多遍了，
**你要遵循真实世界物理规则，你犯的很多错误都是这个原理**」。

我当时的判词是「手指细长像爪」—— **我根本没数**。四张产物全部只有 4 根手指、没有拇指。

| 我的判词（观感） | 实际的物理错误 | 为什么漏 |
|---|---|---|
| 手指细长像爪 | **每只手只有 4 根手指** | 没数 |
| 有动作，达标 | 背景动得是人物 2.3 倍 | 用整帧平均，分不清人和背景 |
| 布料质感不够 | 服装不符合真实世界物理 | 没有布料物理判据 |

> **观感是连续的、可辩解的；物理规则是离散的、可数的。**
> **能数的必须数，不能靠「看起来还行」。**

**完整检查表**：`00_治理与登记/物产验收-物理规则检查表.md`
六节：解剖（可数）/ 物体存在性 / 布料重力 / 光照一致 / 视频专属 / 合规。

**最常漏的三条**：
1. **手指每只手 5 根**（4 指 + 1 拇指，拇指与其余四指不同侧）—— **放大到手部占屏 1/3 逐根数**
2. **双眼同色**（除非原设异色瞳，如芙宁娜）
3. **待机视频的背景不该动**（背景/人物帧差 ≤0.6）

⚠️ **判废闸自动查不了手指数** —— 它只数手的 bbox 数量，4 指 5 指都算 1 只手。**必须人工数。**

## 二、六类 prompt 陷阱（一天栽五次，全部实测）

| 错法 | 后果 | 正解 |
|---|---|---|
| `official outfit, canon design` | **出全裸** | 不是 Danbooru 词汇，CLIP 不认。有 LoRA 时**别写**服装元描述，LoRA 已带 |
| `both eyes same color` | 异色瞳压不住 | 同上，无效自然语言。只写 `light blue eyes`，靠负向 `(heterochromia:1.8)` |
| `no teal, no green tint` | **整图变青绿霓虹** | **"no X" 在正向里不是否定，是强调 X**。否定只能进负向 |
| `open palms, fingers relaxed and spread` | **人变 T 字摊手站姿**，毁姿势轴 | 只写 `empty hands,` 就够 |
| **`eye level camera`** | **窗台凭空长出一台相机**（§三定死） | 机位只用 Danbooru 真 tag：**`straight-on`** / `from above` / `from side` |
| **`frog buttons`**（盘扣的标准英译） | **裙上爬三只青蛙**，连发饰都变青蛙 | 只写 `mandarin collar, side slit`；词有第二义项就别用（§三之二） |

**判据两问，缺一不可**：
1. **这词在 Danbooru 有没有对应 tag？** 没有 → CLIP 不认，等于没写（甚至反向生效）
2. **这词有没有第二个更常见的具象义项？** 有 → 模型多半画那个（frog / camera 都栽在这条）

## ★★ 负向词权重过高会**反向溢出**（2026-08-24 实测，反直觉）

**`(heterochromia:1.8)` 写在负向里，反而把异色瞳招了出来。**

生产批 8 张里 5 张异色瞳（甘雨/刻晴/莫娜），负向明明有 `(heterochromia:1.8)`。
704×1280 · 甘雨 · seed 424242 固定，六档单变量：

| 档 | 改了什么 | 异色瞳 | 过曝% |
|---|---|---|---|
| A 现状 | — | 🔴 左红右蓝 | 2.62 |
| **B** | **负向权重 1.8 → 1.2** | ✅ **消失** | 2.21 |
| **C** | **负向改多个同义词、全不加权** | ✅ **消失** | 2.72 |
| D | 去厚涂词族（保留 1.8） | 🔴 | 0.41 |
| E | LoRA 0.8→0.6（保留 1.8） | 🔴 | 1.49 |
| F | 去 backlighting（保留 1.8） | 🔴 | **0.36** |

**D/E/F 都保留 1.8，全部还有异色瞳 —— 干净地排除了厚涂、LoRA、逆光三个嫌疑。**

### 推广结论
**负向词不是「权重越高越管用」。** 过高的负向引导会让该特征以扭曲形式出现。
**负向权重上限 1.4；要加强就加同义词，不要加权重。**

```
❌ (heterochromia:1.8)
✅ heterochromia, different colored eyes, odd eyes, multicolored eyes, two-tone eyes
```

### ⚠️ 这个缺陷只在生产分辨率复现
512×768 双眼正常，704×1280 才出异色瞳。
**又一次印证「最小复现第 0 步：先确认缺陷在缩小条件下仍复现」** —— 这次执行了，没白跑。

## ★ 过曝的真凶是 `backlighting`

同组实测：去掉 `backlighting` 后过曝像素占比 **2.62% → 0.36%**。
但逆光是 BLOG-031 画风的核心成分，**不能删，要降权 + 负向兜**：

```
正向  backlighting               ← 不加权（原来是 1.15）
负向  overexposed, blown out highlights, washed out, blown out background
```

**判据**：`≥245 亮度的像素占比`，超过 **1.5%** 就是过曝（正常档在 0.4-1.0%）。

## 三、凭空出现的道具（相机）—— ✅ 已定死：`eye level camera`

**真凶是正向里的 `(eye level camera:1.2)` 自带 "camera" 一词。**
负向 `(camera:1.5)` 压不住，因为正向正以 1.2 权重点名要它。

**证据**（2026-08-24，704×1280 生产分辨率，单变量对照，seed 424242 固定）：

| 组 | 机位词 | 结果 |
|---|---|---|
| A | `(eye level camera:1.2)` | 🔴 窗台出现红色相机 |
| B | **`(straight-on:1.2)`** | ✅ 相机消失 |

其余 prompt、场景、参数、种子**完全相同**。

**正解**：机位一律用 Danbooru 真 tag —— `straight-on` / `from above` / `from side` /
`from behind` / `dutch angle`。**任何含 "camera" 字样的写法都不许进正向。**

### 归因反复过两次，方法论比结论值钱

1. 首次归因「室内木窗台的语料关联」→ **错**。换户外后相机照样出现
2. 二次最小复现降到 512×768 → **实验是空的**。缺陷在低分辨率根本不复现
3. 三次在 **704×1280 生产分辨率**做单变量对照 → 定死

> **教训一：单次观察不构成因果。** 概率性缺陷在单样本上「消失」是必然会发生的巧合。
> **教训二：最小复现的第 0 步是先确认「缺陷在缩小后的条件下仍然复现」。**
> 确认不了就不能缩 —— 缩了只会得到一组看起来干净、实际什么也没证明的图。

## 三之二、词存在 ≠ 词是你以为的意思（比「不是 tag」更阴的陷阱）

`frog buttons` 是**盘扣的标准英文译名**，词本身没错。
但模型把它理解成了字面的**青蛙** —— 旗袍上爬了三只绿青蛙（P 和 Q 两档同时复现）。

同族风险词：`frog`(盘扣) · `mandarin collar`(立领，还算安全) · `shell`(贝壳/弹壳) ·
`crane`(鹤/起重机) · `fan`(扇子/风扇) · `mouse`(鼠标/老鼠)。

**判据升级**：不只问「这词在 Danbooru 有没有 tag」，还要问
**「这词有没有第二个更常见的具象义项」** —— 有的话模型多半画那个。

## 三之二点五、★ 加词族会稀释姿势 —— 两组独立实验同向证实

**机制**：prompt 里的注意力是**零和**的。多塞 15 个画风 token 进去，
角色 tag 与姿势 tag 分到的权重就被摊薄，于是**姿势散掉、标志配件丢失**。

| 实验 | 加了什么 | 姿势后果 |
|---|---|---|
| R / S 档 | 通用画风词族（cinematic/rim light/bloom/pixiv trending…） | 「肩靠墙侧看」→ 两手往两边摊；鬼面发饰丢失 |
| C1 → C3 | 厚涂 + 光影词族 | 上身转开更多，擦边风险升高（**抬腿是基础 prompt 的锅，C1 就有，不算这条的证据**） |

**这不是画风词的错，是权重分配的错。**

⚠️ **归因纪律**：R/S 那组是有效证据（P 与 R 姿势明显不同）；
C1→C3 那组我一开始也算进来了，**四张并排一看抬腿是 C1 就有的**，
来自基础 prompt 的 `weight on one leg` + `long legs:1.35`，跟画风词无关。
**并排看四张只花 10 秒，比逐张看可靠得多 —— 逐张看极易把「一直存在的」当成「新出现的」。**

### ★ prompt 通道会到顶 —— 这不是调参能解决的

2026-08-24 实测：同一张图上，**L 轴标志特征（保身份）与厚涂词族（保画风）互相稀释**。
两组词都是必须写的、都是正确设计，但它们抢同一份注意力，加在一起就互相削。

对照：纯厚涂（不写 L 轴）画风最强 → 加上 L 轴后画风回落一档，身份变强。

> **这是 prompt 通道的容量上限，不是权重没调好。** 继续在 prompt 里加减词是零和游戏。

**出路：把姿势从 prompt 里搬走。**
姿势现在占着 `(<姿势>:1.45)` + `(straight-on:1.15)` + `(full body, feet visible:1.2)` 三组权重。
接上 **ControlNet-OpenPose**（权重 2.5GB 已下载冷备在 SMB，工作流一直没接）后，
这三组的份额可以全部让给身份与画风。

**这是接 ControlNet 的最强理由 —— 不是「姿势更准」，是「腾出 prompt 预算」。**

### 另一条独立的姿势坑：`long legs` + `weight on one leg`

复刻四档全部抬腿，根因在这两个词：
- `long legs` 被模型夸张化成腿部特写
- `weight on one leg`（想表达重心偏移/contrapposto）被理解成**把一条腿抬起来**

**正解**：重心偏移用 Danbooru 真 tag **`contrapposto`**；腿部比例交给景别与构图，别写 `long legs`。

**正解（三选一，别只加不减）**：
1. **同时把姿势 tag 权重顶上去**：`(<姿势>:1.45)` 而不是 1.3
2. **控制词族长度** —— 厚涂只留核心 3–4 个词，别把 bloom/particles/trending 这类通用增强词也塞进去（底模已内化，纯稀释）
3. **姿势用 ControlNet-OpenPose 锁死**，把姿势从 prompt 里拿出来（权重已下 2.5GB，工作流未接 —— 这是接它的最强理由）

> **判据**：加任何词族之后，**第一件事是看姿势有没有变**，不是看画风有没有变。
> 画风的收益很容易被姿势的损失抵消到负。

## 三之三、变体：白底那套 SSIM 窗对带背景的图不适用

**RULE-034-001 的「同构图 2 变体 SSIM 0.39–0.43」是白底产物，别照抄。**

实测（`规格校验.py`）：

| | 两帧共同近白区 | SSIM |
|---|---|---|
| BLOG-034 原图三对 | **40.7–44.1%** | 0.39–0.43 |
| 我方带背景产物 | **0.6–1.8%** | 0.18–0.24 |

原图有 ~42% 画面是同一片纯白，**这块面积白送 SSIM**。带背景的图没有这份免费分，
同样质量的变体只能拿到 0.22 —— **不是变体不好，是尺子不可比。**

### 带背景该用什么判据
**边框带的结构相似度**（`规格校验.py` 的 `scene_family`，外圈 16%，量 SSIM 结构分量）。
阈值 **0.70**，用正负对照标定：

| 对照 | 分数 |
|---|---|
| 真·正：对标原图两帧（确定是一组变体） | 0.778 / 0.776 |
| 我方 i2i denoise 0.55 | **0.780** ← 与原图同水平 |
| 我方 txt2img 换姿势（场景跟着飘） | 0.620 |
| 真·负：场景完全不同 | 0.556 / 0.616 |

### ★ 变体的死结：姿势与背景在同一个通道里争

| 做法 | 背景 | 姿势 |
|---|---|---|
| txt2img 换姿势词 | 🔴 跟着飘（0.62） | ✅ 真的变了 |
| img2img denoise 0.55 | ✅ 守住（0.78） | 🔴 几乎没变 |
| img2img denoise 0.85 | 🔴 飘了（0.64）+ 服装也变了 | ✅ 变了 |

**两条路都通不了。解法是 ControlNet-OpenPose** —— 姿势变成外部约束，
i2i 低 denoise 守背景，两件事就不抢了。

> **这和「prompt 预算不够分给身份+画风」是同一个瓶颈的两个面，同一个解。**
> ControlNet 权重 2.5GB 已下冷备，工作流未接 —— **现在有两条独立理由了。**

### 我在这上面返工了三次，记下来防再犯
1. 变体用了**不同 seed** —— 我自己早测出「换 seed = 0.23」，却没在代码里执行
2. 场景判据 v1 量整图色彩直方图 —— **被人物主导**，负对照打回
3. 场景判据 v2 量边框带色彩 —— **i2i 会整体提亮**，颜色恰是变化最大的维度，又打回

> **指标先跑正负对照再用。三次都是靠负对照发现错的，没有一次是靠推理。**

## 七、判据（与 character-skin-pipeline 共用）

1. **判产物在不在 → 扫盘**，不看 ComfyUI history（内存态，重启即清）
2. **判已完成 → 回读校验**，`status_str: success` 不算数；3840×2160 的 PNG 只有 ~27KB 或 64px 压缩后 <1200B = 纯色废图
3. **红线无可靠自动判据** —— 视觉 API 不稳、肤色占比判据实测校准是反的（红线图 7%、正常图 84%）。**一律人工逐张过，不许自动升「已验收」**
4. **交付格式必须通用可播** —— `SaveAnimatedWEBP` 出的是 VP9，很多播放器打不开。出片一律同时转 H.264 MP4 + GIF
