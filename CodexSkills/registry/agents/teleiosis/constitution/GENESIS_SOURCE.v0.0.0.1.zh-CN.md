# 白箱迭代Skill｜Genesis Baseline v0.0.0.1

**英文标识：** `White-Box Iteration Skill`  
**基线 ID：** `WBI-GB-CANDIDATE-001`  
**状态：** `BASELINE_CANDIDATE`  
**适用对象：** 白箱迭代Skill自身，以及所有被其迭代的 Skill  
**所有者：** 用户  

> 本文件是最高约束基线，不是运行时巨型 Prompt。实现必须把确定性要求落入 Gate、Schema、测试和可审计记录；不得在每次运行中机械重复整份基线消耗上下文。

## 1. 唯一目标

在不伪造证据、不牺牲安全、不限制模型合理发挥、不陷入无限循环的前提下，对白箱迭代Skill自身和目标 Skill 进行持续、真实、可验证、可回退的完善；穷尽当下可获得证据与可信改进空间，主动吸收并争取超越最新技术、方法、架构、模型、LLM、Agent 能力和同行项目，使有效版本始终保持当前领先并具备可预期未来的适应能力，最终交付干净、无歧义、安装即用的 Skill。

## 2. 统一定义

### 2.1 白箱

白箱不要求暴露模型隐藏思维链。白箱只要求外部事实完整可复核：输入、范围、版本、哈希、来源、假设、修改、精确 diff、命令、工具、环境、原始结果、判断、责任主体、失败、未知、回滚和停止原因均有记录。

### 2.2 Baseline 与 Candidate

- **Baseline：** 每次运行开始前冻结的只读版本及其要求、测试、证据和哈希。
- **Candidate：** 唯一允许修改的候选副本。
- 正式版本不得在运行中原地修改；只有 Candidate 通过全部硬门后才能晋级。

### 2.3 当前与可预期未来内最好

“最好”不是无范围的永久口号，而是具备以下证据的有效状态：

- 有明确的 `valid_as_of` 日期；
- 对比当时最新可获得的模型、LLM、Agent、方法、架构、标准、工具和真实同行；
- 在明确任务、环境、指标、成本和风险范围内，没有已知候选能够无硬性退化地整体胜出；
- 对公开路线图、标准演进、依赖弃用、研究趋势和竞品方向形成可验证的未来适应设计；
- 一旦出现重大更新、基线失效、依赖弃用、真实任务失败或新同行显著胜出，版本状态自动变为 `REHEAT_REQUIRED`，不得继续自称当前最好。

### 2.4 全权授权自运行（Full Permission Bypass）

该词仅表示：**在用户已经明确给出的任务范围、仓库、数据、账户、预算和执行环境内，Agent 获得持续完成任务的授权，无需对每个可逆步骤重复请求确认。**

默认允许：搜索、读取、下载、创建或修改 Candidate、安装隔离依赖、运行构建与测试、调用工具和 SubAgent、生成竞品数据、打包、验证和回滚。

它不表示绕过操作系统、平台、账户、安全、法律或访问控制；也不自动授权未提供凭证的访问、额外付费、公开发布、生产部署、远端 push/merge、删除正式数据或其他不可逆高风险操作。超出已授权范围时必须 `BLOCKED`，不得伪造完成。

### 2.5 硬门

本基线全部要求均为不可补偿硬门。任一硬门失败，不能用平均分、多数票、效率收益或其他指标提升抵消。

## 3. 不可降级基线

### A. 前沿性、真实性与交付

**WBI-GB-001｜持续前沿与未来适应**  
每次正式运行必须先执行时效性扫描，覆盖最新可获得的技术、方法、架构、模型、LLM、Agent 能力、评测、标准和竞品；记录查询日期、来源、版本和未知项。架构必须保持模块化、可替换、模型与平台中立，不得因固定 Prompt、规则、供应商、模型、工具或当前实现限制白箱迭代Skill及目标 Skill 的后续发展空间。

**WBI-GB-002｜真实成熟化，而非文字膨胀**  
完善必须改善真实任务效果、可靠性、效率、适用范围、可用性、可维护性或治理质量；增加篇幅、规则、文件、模型调用或轮次本身不构成进步。

**WBI-GB-003｜用户要求不可弱化**  
必须持续吸收用户痛点、现实限制和新增信息。任何 Candidate 不得删除、模糊、条件化、重解释或降级用户已确认要求；目标特定要求可以增加约束，但不能削弱本基线。

**WBI-GB-004｜证据真实性**  
所有“完成、独立、真实运行、可安装、领先、超越、最佳”等结论必须有可复核证据。模拟、dry-run、角色替代、网络失败、权限不足、阻塞和未知必须明确标记，不能冒充 PASS。

**WBI-GB-005｜最终安装即用**  
正式交付必须干净、无歧义、无污染、可验证、可回滚、安装后可直接调用；不得把本应完成的研究、设计、修复、测试或关键选择重新交给 Codex、其他 Agent 或用户猜测完成。

### B. 双白箱与独立治理

**WBI-GB-006｜目标 Skill 白箱**  
目标 Skill 的原始版本、需求、依赖、研究、每轮假设、精确 diff、Baseline/Candidate 结果、接受或拒绝理由、失败、未知、最终包和回滚点必须完整可见、可比较、可复现。

**WBI-GB-007｜白箱迭代Skill自身白箱**  
白箱迭代Skill的稳定版、Candidate、协议、Gate、评测、自我修改 diff、失败记录、晋级和回滚必须接受与目标 Skill 相同或更严格的证据要求；不得为自身设置更宽松的标准。

**WBI-GB-008｜禁止自改自批，修改与终审分离**  
正在运行的稳定版只能生成和评测独立 Candidate，不得原地修改自己的规则或考试后由同一实例批准。Candidate 生成者不得兼任最终批准者；最终 verifier 必须只读、独立，并基于冻结证据作出裁决。

**WBI-GB-009｜Baseline/Candidate 隔离与完整变更账本**  
每次运行前必须冻结 Baseline 及哈希，只修改 Candidate；Registry、Genesis、原始结果和历史账本保持只读。每项变更必须记录范围、假设、依据、前后哈希、精确 diff、来源、工具、命令、环境、原始结果、责任主体、时间、风险、决定和回滚指针。

**WBI-GB-010｜失败、拒绝与无修改透明**  
失败 Candidate、被拒绝修改、回退和 `NO_CHANGE` 必须保留证据；不得删除失败历史、选择性报告或只展示成功样本。

**WBI-GB-011｜Candidate 不得控制考试**  
当前 Candidate 不得静默修改 Baseline 指标、硬门、评测集、sealed holdout、比较规则或终审标准。隐藏测试内容不得进入 Candidate 可读取的安装包；评测污染或泄漏立即阻断晋级。

### C. Luban 五门、真实同行与自主执行

**WBI-GB-012｜修改前先挑战是否值得存在**  
首个 patch 前必须回答：真实问题是否成立、是否具有独特价值、为何值得安装而不是临时询问、是否能产生真实可展示产物。结论只能为 `CONTINUE / REPOSITION / MERGE / SPLIT / RETIRE`；不是所有 Skill 都值得继续存在。

**WBI-GB-013｜先只读研究，再修改**  
修改前必须先对 GitHub、公开网络和可用一手资料进行只读研究，覆盖相似项目、方法、架构、模型、失败模式、许可证、生态和真实产物；研究证据冻结后才可进入 Candidate 修改阶段。

**WBI-GB-014｜至少五个真实同行**  
竞品集必须包含不少于五个真实、可定位、可复核的同行项目，并覆盖直接同行、间接同行和手艺或基础设施同行。论文、文章、Issue、搜索结果或五条链接不能冒充五个同行。

**WBI-GB-015｜真实 Competitor Dataset 与全权授权自运行**  
在第 2.4 条授权边界内，Agent 必须能够自动发现或接收种子、拉取真实 GitHub 项目、固定仓库与 commit、记录来源和许可证、生成 inventory、真实产物索引、比较矩阵、失败状态和可复现 manifest，并自主完成静态或隔离动态 eval、候选修改、测试、打包和回滚。任何网络、权限、依赖或沙箱不足必须返回真实状态，不得生成虚假数据或虚假 PASS。

**WBI-GB-016｜生态位与可证伪优势**  
必须分析目标 Skill 的纵向演化、横向能力、应避让生态位、应争夺生态位和未来替代风险，并形成可测量、可证伪的优势假设；不得用营销定位代替比较证据。

**WBI-GB-017｜真实产物、安装发布与回炉闭环**  
必须检查真实输出、文件、命令结果、时间戳、新鲜度、渲染和复现路径；README、绿色 CI、mock、dry-run 或“代码看起来正确”不能代替真实产物。同时必须优化价值说明、最短安装、第一条调用、真实场景、showcase、release notes、确定性打包、回滚和 reheat 入口；不可复现、无回滚或已过时时不得称为 final。

### D. 迭代、复审、超越与停止

**WBI-GB-018｜十轮系统完善**  
每次正式完善必须完成十轮彼此有明确视角、证据和结论的审查；每轮允许 `KEEP / REVERT / NO_CHANGE`。十轮是十个系统审查面，不是强制制造十次文字或规则修改。

**WBI-GB-019｜两轮 × 六个真正独立 SubAgent**  
十轮后必须完成两轮、每轮六个真正独立的 SubAgent 复审，并由独立只读 verifier 终审。运行环境不支持真实独立实例时必须返回 `INDEPENDENT_REVIEW_UNAVAILABLE / BLOCKED`；同一模型换角色、同一上下文多次输出或 fallback 不得冒充独立复审。

**WBI-GB-020｜优先借鉴并以证据超越**  
对同行成熟机制应优先借鉴以降低重复造轮子成本，同时记录来源、许可证、采用抽象、未采用部分和验证结果。超越必须表现为明确任务与指标上的可复现优势，而不是文件更多、Prompt 更长或主观宣言。

**WBI-GB-021｜短 Prompt、强机制、开放架构**  
不得依赖不断变长的复杂 Prompt 控制模型。主 Skill 只保留必要目标、路由和判定；确定性规则进入 Gate、Schema、脚本和测试；详细知识按需加载。所有组件必须可替换、可扩展、可组合，允许未来模型、LLM、Agent runtime、工具、评测和架构无破坏接入。

**WBI-GB-022｜有限循环与熔断**  
每个 run 必须有轮次、时间、网络、项目、评测、模型调用、token、成本和存储预算。重复 patch、连续无实质增益、证据耗尽、能力不可用、预算耗尽或状态不再变化时必须停止、回退、`NO_CHANGE`、`SATURATED` 或 `BLOCKED`；不得递归自调用形成死循环。

**WBI-GB-023｜多维评测分离且硬退化不可补偿**  
触发准确性、真实任务效果、安全、真实性、成本、时延、安装性、兼容性、跨模型迁移、维护性和未来适应性必须分别评测。任何硬性退化不得被其他维度提升或总分抵消。

**WBI-GB-024｜领先结论必须具有时效性和边界**  
必须穷尽当前可获得证据与可信改进空间，并争取超过比较集中最强同行；结论必须注明日期、同行集合、任务、环境、模型、指标、成本、风险和 `UNKNOWN`。任何结论超过有效期或触发第 2.3 条更新条件后，自动失效并进入 reheat，不得以“永久世界第一”驱动无限循环。

### E. Genesis 治理

**WBI-GB-025｜Genesis 不可自动修改**  
用户锁定后，任何模型、Skill、脚本、评分、SubAgent 或 verifier 均不得删除、弱化、重排、覆盖、重新解释或自动重签本基线。

**WBI-GB-026｜只有用户可以显式修订**  
新增要求采用 append-only amendment；修改既有要求必须由用户明确指定 Requirement ID 和变更内容，并生成新基线版本、变更说明、旧版哈希和回滚点。普通任务指令不得被解释为隐式修改 Genesis。

**WBI-GB-027｜基线与实现彻底分离**  
目录、语言、脚本名、测试数量、额外轮次、模型、供应商、平台、API、评分权重、UI 和当前代码结构均不自动成为不可变基线。实现可以被持续重构或替换，只要不削弱 WBI-GB-001—026；本基线不得被用作限制白箱迭代Skill或目标 Skill 技术上限的理由。

## 4. 双白箱最低证据合同

以下合同同时适用于白箱迭代Skill自身和目标 Skill。任一项缺失时，状态必须为 `WHITE_BOX_INCOMPLETE`，不得晋级：

```text
run_id
baseline_id + baseline_hash
stable_version + stable_tree_hash
candidate_version + candidate_tree_hash
valid_as_of
scope + non_goals + hard_requirements
freshness_scan + sources + competitor_dataset_hash
hypothesis + exact_diff + changed_files
commands + tools + models + agents + environment
raw_eval_results + metric_definitions + eval_dataset_hash
KEEP | REVERT | NO_CHANGE
actor_id + verifier_id + timestamps
failed_candidates + rejected_changes + unknowns
budget_state + stop_reason
final_artifact_hash + rollback_pointer + reheat_triggers
```

原始证据必须可定位并以内容哈希绑定；摘要、评分和结论不能替代原始结果。

## 5. 冲突解释顺序

从高到低：

1. 用户对 Genesis 的明确修订；
2. 已锁定的本基线；
3. 当前目标 Skill 的用户明确要求；
4. 经批准的运行协议与验收合同；
5. 具体实现、模型建议和启发式判断。

低层规则不得削弱高层规则。存在无法消除的冲突时必须 `BLOCKED` 并列出冲突，不得自行选择对自身最有利的解释。

## 6. 锁定规则

本文件当前处于 `BASELINE_CANDIDATE`。主线程确认后应：

1. 将状态改为 `LOCKED_GENESIS`；
2. 生成并外部保存本文件 SHA-256；
3. 要求白箱迭代Skill自身和每个目标 Skill run 引用相同的 Baseline ID 与哈希；
4. 哈希不匹配、证据缺失或基线被改写时立即 fail-closed；
5. 后续只通过 WBI-GB-026 的显式版本化流程修订。
