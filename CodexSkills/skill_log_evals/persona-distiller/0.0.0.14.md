## 触发这次迭代的缺陷

**用户点名**：公开树同时声明多个版本号，且 SKILL metadata 与正文的输入合同冲突。

实测结果比点名的更宽——**同一个 skill 对外声明了 7 个不同的版本号**：

| 位置 | 值 | 性质 |
|---|---|---|
| `CodexSkills/registry/index.json` | `0.0.0.4` | 机读·总索引 |
| `registry.yaml`（index.json 指向的入口） | `0.0.0.5` | 机读·registry 入口 |
| `VERIFICATION.md` / `handoff.md` / `PACKAGE_MANIFEST.json:version` | `v0.0.0.5` | |
| `README.md` | `v0.0.0.6` | |
| `SKILL.md` 正文首个小节标题 | `v0.0.0.7` | |
| `VERSION` / `manifest.json` / `PACKAGE_MANIFEST.json:distribution.kind` | `v0.0.0.13` | |

**衰减是单调的：离发布脚本越远的位置越旧。**

根因不是有人偷懒，而是 `self_check.py` 的版本校验**只比 `VERSION` 与 `manifest.json` 两处**。
v0.0.0.8 的记录写着「版本已建立单一真源」，实际建立的是**两点之间的一致**；
另外六处从来没有任何东西查过。**只覆盖 2/8 的单一真源，不是单一真源。**

`PACKAGE_MANIFEST.json` 更是**同一个文件里两个版本号自相矛盾**：
`build_manifest.py` 只用 `VERSION` 盖 `distribution.kind`，
从不覆盖 `version` 字段——于是那个字段从 v0.0.0.5 起冻了 9 个版本。

### 比版本更严重的一类：输入合同自相矛盾

`SKILL.md` 的 metadata（调用方唯一会读的那份）写：

> Required inputs are the target person's name and one identity family
> **or weighted multi-identity selection**

同一文件的正文写：**「十二个主身份之一（单一主身份；多重身份已移除）」**，
且 `test_weighted_selection_is_rejected` 这条用例一直是绿的——
**代码确实拒绝加权多身份，只有对外的合同还在提供它。**

`registry.yaml` 把已删除的 `多重身份` 目录连同 6 个旧族名列为 `persistent_output`，
`CONTRIBUTING.md` 仍写 `seven-family unique registry`。

## 交付物

### `scripts/check_contract_drift.py`（新，硬门）

查三件事：

1. **skill_version 单一真源** —— 8 个对外声明位置全部必须等于 `VERSION`
2. **builder_version 单一真源** —— 凡自称在讲交付合同的行，版本必须等于 `persona_registry.BUILDER_VERSION`
3. **身份输入合同** —— metadata 不得出现多身份词族；族数声明必须等于 `identity-families.json` 的条目数；`registry.yaml` 不得列出磁盘上不存在的身份目录

**三个轴不能互相顶替**，这正是原来那行 README 的病：

> ~~v0.0.0.6 将身份分类……交付合同格式不变，仍为 v0.0.0.5~~

一行里同时出现 skill 轴和 builder 轴的版本号 —— 本检查器把它单列为 `[轴混写]` 判定。

分轴靠既有书写约定：**builder 带 `v`、人物产物裸写 `0.0.0.1..0.0.0.999`**。
若将来有人把人物版本写成 `v0.0.0.1`，本检查器会误报——
**那时应当修书写约定，而不是放宽本判据**（约定已写进检查器 docstring）。

### 接进 `self_check.py`

独立脚本不是门（v0.0.0.10 的教训）。现在漂移是 `self_check` 的 error，不是 warning。

### 3 条回归用例（`tests/test_skill_contract.py`）

`test_declared_version_has_exactly_one_source_of_truth`、
`test_contract_drift_gate_has_a_working_negative_control`、
`test_skill_metadata_does_not_offer_removed_multi_identity_input`。

### 判据选择：出现即报，不做否定式识别

改后的 description 一度写成「weighted multi-identity selection **was removed and is rejected**」——
仍被门拦下。这是**故意的**：想区分「肯定提供」与「明确否定」得用字符串认否定语气，
而「正则写窄 → 命中为 0 → 断言不存在」是 RUNBOOK 里复发过十二次的失败模式。
代价只是 metadata 不能写否定句（那句话本就该放正文），换来判据可机检。

## 未解决：发行 bundle 自 v0.0.0.9 起构建不出来

剩下 2 个 failed 用例同一个根因，**也是同一种病，但后果重得多**：

```
build_release_bundle.py → SystemExit: version mismatch: .../persona-distiller-group
```

`build_release_bundle.py` 要求两个 Skill 的 `VERSION` 完全相等：
- `persona-distiller/VERSION` = `v0.0.0.14`
- `persona-distiller-group/VERSION` = `v0.0.0.8`

v0.0.0.9 之后的改动只落在 builder 一侧，group 没跟着动，
**于是从 v0.0.0.9 起 `PersonaDistiller-Final-*.zip` 一次也构建不出来。**
此前没被发现，是因为它的 2 个失败用例一直混在另外 3 个校验和失败里
——**这正是 RUNBOOK 第二十二种「修法只落在被抓到的那一处」的镜像：
失败也会藏在别的失败后面。**

**未擅自修复**，因为修法取决于一个尚未裁定的语义问题：
bundle 版本号是「一个号盖两个 Skill」，还是「两个 Skill 各自编号、bundle 只记录两者」。
把 group 从 v0.0.0.8 直接抬到 v0.0.0.14，等于凭空宣称 6 次没有发生过的 group 发布。
并入任务 #26（group 的 CHANGELOG / manifest 版本字段）一起裁定。

## 已知缺口（写下来，不假装没有）

1. **正文里的历史版本标记只做了改写，没有落成判据。** `SKILL.md` 的
   `## 【v0.0.0.7 新增硬门】` 改成了 `【自 v0.0.0.7 起的硬门】`，
   但「正文里的版本号是历史陈述还是当前声明」**只能是散文**——
   要机器判定得读语义，而不是读字符串。门只覆盖**首行标题与结构化字段**。
2. **`registry.yaml` 的 `verification` 段仍是陈旧的 0**
   （`offline_tests: 0`，实际 59）。本轮未纳入判据：那几个数应当由
   `self_check` 的实跑结果回写，而不是手填——手填的数字下一次照样会陈旧。
   这本身是下一版的候选。
3. **builder 轴的判据是按行扫的，认不出「标题的管辖范围」。**
   `VERIFICATION.md` 里「最终发行只产生 `PersonaDistiller-Final-v0.0.0.5.zip`」
   这句写在 `## v0.0.0.5 交付合同` 标题下、句内不含关键词，于是没被扫到——
   而它是错的：bundle 名跟随 **skill 发布号**（`build_release_bundle.py` 从 `VERSION` 读）。
   本轮手工订正了这一句；判据要覆盖它得引入标题作用域，尚未落成。
4. 本门只查 `persona-distiller`，**不查 `persona-distiller-group`**。
   group 缺 CHANGELOG 与 manifest 版本字段（任务 #26），
   它的版本号目前仍是 `VERSION` 单一来源、未经交叉核对。
