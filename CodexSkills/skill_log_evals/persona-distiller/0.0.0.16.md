## 交付物一：第四类归属证据 `A-masthead`

**加判据的时候最容易顺手把门放松。这里三重约束缺一不可：**

1. **必须显式声明**（`meta.json` 的 `single_author_masthead`）——
   检查器绝不自行推断站点名。放 meta 不放命令行开关，是因为它必须随工作区走、
   可审计、事后能被复核。
2. **报头必须含人物的名或姓**——`Seth's Blog` 含 `Seth` 才配声明。
   **Steinhardt 那轮的 `CONTACT` 刊头不含 `Steinhardt`，在声明阶段就被 `ValueError` 拒掉**，
   于是那四份别人写的随笔照旧拦得住。这一条是整个设计的承重点。
3. **反向检查照常生效**——文末出现别人的身份署名一样降级。

一句话：放行的是「以他本人命名的单作者站点」，不是「任何有刊头的出版物」。

负对照从 **4 正 4 反**扩到 **5 正 7 反**，新增三条全部针对这一类：

```
  ✓ 正例 单作者站点报头: A-masthead
  ✓ 反例 报头在，但文末是别人的署名: 已拒
  ✓ 反例 报头只出现在句子中间，不是结构位置: 已拒
  ✓ 反例 不含人物名的刊头: 已拒绝声明
```

最后一条是**在声明阶段**拒，不是在判定阶段拒——差别在于它连试都试不了。

## 交付物三：`bump_version.py` 不再改 `VERIFICATION.md` 的标题

**这是我自己那个工具当场犯的错。** 升 v0.0.0.16 时它照例把
`VERIFICATION.md` 的首行改成了新版本号，而正文还是 v0.0.0.14 那轮的：
写着 **PARTIAL**、写着 bundle 构不出来、写着 97 人 / 59 用例——
**这三件当时都已不成立**（v0.0.0.15 已解绑锁步，人数已到 98，用例已到 64）。

**改过标题的旧正文，比标题陈旧更糟。** 陈旧标题一眼看得出；
改过标题的旧正文会冒充当前复验，而它恰恰是别人用来判断「这个版本验过没有」的那份文件。

修法不是让工具去改正文（它没有那个信息），而是**让它不要碰**：

- `VERIFICATION.md` 从自动改名清单里移除，改为打印一条警告
- **`check_contract_drift.py` 仍然要求它的标题等于 `VERSION`**——
  于是漂移照报，压力从「工具替你变绿」变成「你必须真的重跑验证」

正确的压力方向是后者。已按本次实跑重写 `VERIFICATION.md` 全文，结果为 **PASS**。

## 已知缺口（写下来，不假装没有）

1. **镜像判据只查「是否相同」，不查「哪一份是对的」。**
   本轮是人工判断「改进都在 `references/`」才定的同步方向。
   如果两份各有一半改进，这个门只会说它们不同，不会说该往哪边合。
   **更根本的修法是消灭其中一份**（让 `references/` 成为符号链接或纯文档引用），
   本轮没做——它会动到打包清单与安装器，不该和归属门挤在一个版本里。
2. **`A-masthead` 依赖「站点名含人物名」这个巧合。**
   `Seth's Blog` 恰好含 `Seth`。若某人的单作者站点叫 `Stratechery` 这类
   不含本人名字的名号，这一类判据用不了，只能退回散文说明。
   **不打算为此放宽**——放宽的代价是多作者刊物重新变得可洗白。
3. **`register_persona.py` 与 group README 的登记表之间没有绑定。**
   本轮靠一条测试抓到，但那条测试是在 `persona-distiller` 的套件里，
   而登记动作发生在 group——**跨 skill 的因果没有门**。
