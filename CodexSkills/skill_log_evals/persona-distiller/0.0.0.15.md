## 触发这次迭代的缺陷

v0.0.0.14 把「发行 bundle 构建不出来」记为未解决，并列了两条修法请用户裁定。
**用户给出的不是选项，而是原始意图**——那条相等判据本意是：

> 确保专家团队中的专家人物，是使用**正确的人物蒸馏版本**蒸馏出来的。
> 比如人物蒸馏已经是 008 了，专家团队就不应该是用 006、007 蒸出来的。

意图完全正确。**判据测的不是那件事。**

| | 想保证的属性 | 实际测的代理量 |
|---|---|---|
| 粒度 | **每个人**由哪个版本产出 | 整个 group 包的**一个数字** |
| 可伪 | 要成立必须真的重蒸 | **改一个文本文件就能满足** |
| 时机 | 入库时就该管 | **打包发行时才触发** |

第一条是最要命的：查全部 97 份 `registration.json`，字段只有 `builder_version`
（钉死 v0.0.0.5）、`product_version`、`model_version`——
**没有任何字段记录「这个人是用哪个蒸馏版本做出来的」**。
那个属性此前根本不落盘，所以那条判据从来就无从测起。

已写进 RUNBOOK **第七十种**：门测的是代理量，而代理量可以在属性不成立时被满足。
识别方法只有一句：**「我能不能在不做那件事的前提下让这个门变绿？」**

## 用户裁定

- 方案 B：每人一条 `distilled_with` ＋ **滚动兼容下限 = 当前版本末位 − 10**
  （`v0.0.0.98` → `0.0.0.88`）
- **低于下限的不重蒸**，只记台账
- **600 人整体完成后统一重蒸所有人**，对齐到当时的最新版本（任务 #29）

## 交付物

### 蒸馏版本随产物走

`delivery_builder.py` 打包时把 `DISTILLER_VERSION`（读自 `VERSION`，不硬编码）
盖进交付 manifest。**不在登记时现取**——登记可能比蒸馏晚很多天，
那时的 `VERSION` 已经不是产出它的那个版本。

### `backfill_distilled_with.py`（group）：回填是推断，必须标注

既有 97 人的交付 manifest 里没有这个字段，只能从 git 重建：
`registration.json` 首次落盘的提交，当时 `persona-distiller/VERSION` 是多少。

**两个已知偏差被显式记进数据**，而不是抹平：

1. 它是「登记时」而非「蒸馏时」的版本
2. 对批量重打包进来的人，它是**上界**——`a31cb12d`（十二族重组）
   把 70 人一次性迁进新目录，**只重打包没重蒸**，正文来自 ≤`v0.0.0.5`

`artifact_created_at` 被明确排除在证据之外：99 条里 **15 条恰好 `00:00:00Z`**、
54 条的分钟数不是 00/30，形态是回填与实测混在一起；
且已核实至少一例与 git 矛盾（`shigeo-shingo` 记 07-24，实际首次落盘 07-26）。

### `check_distillation_freshness.py`：**默认只报不拦**

裁定是「下限以下不重蒸」，所以它不能阻塞发行——否则发行会被自己堵死。
`--strict` 存在但发行流程不用。接进 `self_check` 是 **warning 不是 error**。

### 解绑两处相等判据

`build_release_bundle.py` 改完后全量测试**在另一处红**：
`templates/bundle/install.py` 里有**同一条判据的第二份拷贝**。
这是第二十二种（修法只落在被抓到的那一处）的又一次复发，当场记进 RUNBOOK 第七十种的附带条。

bundle 现在**如实记录两个 Skill 各自的版本号**，外加新鲜度实况：

```json
"persona-distiller-group": { "version": "v0.0.0.8" },
"distillation_freshness": {
  "distiller_version": "v0.0.0.15", "compatibility_floor": "v0.0.0.5",
  "at_or_above_floor": 99, "below_floor": 0, "upper_bound_only": 70,
  "policy": "低于下限不阻塞发行；统一重蒸安排在 600 人整体完成之后"
}
```

摘要函数**复用检查器，不另写一份判据**——同一件事两把尺子迟早分叉，
而分叉那天没有人会发现。

### `bump_version.py`：把 7 处手工替换变成一条命令

**这一条是被自己现场逼出来的。** 升 v0.0.0.15 时我连着漏了两轮：
先漏 `registry.yaml` 与 `index.json`，补完又漏 README / VERIFICATION / handoff
三个标题。`check_contract_drift.py` **每次都抓到了**——
但「抓到」和「不再发生」是两件事，会重复 7 次的手工动作迟早漏第 8 次。

**工具自己也带着这个病的实例**：首版 `rewrite_title` 写成 `line.replace(old, new)`，
于是「`VERSION` 已手工改过、只剩文档没跟上」时 `old == new`，替换成了空操作——
工具报「已改 4 处」而门当场报 3 条漂移。
**修复动作本身要能修复「修了一半的状态」**，否则它只在理想路径上有用。
改成按形态替换（正则匹配 `v\\d+\\.\\d+\\.\\d+\\.\\d+`）后，7 处一次盖全。

## 已知缺口（写下来，不假装没有）

1. **那 70 条上界值没有办法收窄。** 十二族重组只重打包没重蒸，
   而重打包前的原始蒸馏版本没有留下记录。
   收窄的唯一途径就是重蒸——已排进任务 #29（600 人完成后统一做）。
2. **下限只在报表里生效，任何地方都不拦。** 这是裁定要求的，
   但意味着「低于下限」这件事**完全依赖有人去看报表**。
   `self_check` 的 warning 是目前唯一的推送渠道。
3. **`distilled_with` 只覆盖 `persona-distiller` 这一个轴。**
   评委指令版本（`_pipeline/judge_prompts/` v1）、质量矩阵版本
   同样会影响产物可比性，但都没有随产物记录——
   必读里那句「已入库 96 人是用更粗的尺子量的，其分数与 v1 及以后不可比」
   目前仍然只是散文。
4. **`registry.yaml` 的 `verification` 段仍是陈旧的 0**（`offline_tests: 0`，实际 64）。
   与 v0.0.0.14 记录里的同一条缺口，本轮仍未落成——
   那几个数应由 `self_check` 实跑结果回写，手填的下次照样陈旧。
