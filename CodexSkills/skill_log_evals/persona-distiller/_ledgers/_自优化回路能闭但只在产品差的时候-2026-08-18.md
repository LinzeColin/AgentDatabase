# 自优化那条回路**能闭** —— 但它只在「产品表现得差」的时候闭得上

**日期**：2026-08-18　**包**：v0.0.0.43 → **v0.0.0.44**
**起点**：Owner 五条批评里的「自优化迭代无实质收益」。
已知的只是「遥测 0 条、C 从未启用」——**那只说明没人喂过它，不说明它能不能用**。

---

## 1. 先把回路真的跑一遍

★ **只写临时遥测文件**。默认路径 `telemetry/team-outcomes.json` 跑完仍**不存在**，
git 里 0 条改动 —— 这一条在动手前就定死了，写脏它会污染此后所有路由的排序。

```
60 条（12 个切片 × 5，coverage 1.00）
  actual_success = 0.2409（＝匹配排序分）⇒ ECE 0.0000 ⇒ eligible True  ⇒ 实跑 strategy = C
  actual_success = 0.85（一个能用的产品）⇒ ECE 0.6091 ⇒ eligible False ⇒ 实跑 strategy = B
```

**⇒ 机制是通的。** 这不是「没实现」。

## 2. 真因：一个排序分被当成概率

`record_team_outcome.py:95`

```python
routing_scores = [row["marginal_score"] or row["base_score"] for row in members]
predicted      = mean(routing_scores)        # → predicted_success
```

而 C 层门要 `expected_calibration_error <= 0.12`，
ECE = 分箱的 `|mean(predicted) − mean(actual)|` 加权平均。

**`marginal_score` 是排序用的分，不是「这支队伍会成功的概率」。**

| 样本 | predicted 实测 | ⇒ 可启用窗口 |
|---|---|---|
| 72 道 oracle 的 12 个题面 | 0.1559–0.2552 | **0.04–0.38** |
| 名册标签 12 条（判据默认） | 0.2155–0.5160 | **0.10–0.64** |

★ **两份都报，不许只报对自己有利的那份。** 取**对产品最有利**的那份（上沿 0.64）：

```
真实成功率 70% ⇒ ECE 0.1840 ⇒ False
真实成功率 80% ⇒ ECE 0.2840 ⇒ False
真实成功率 90% ⇒ ECE 0.3840 ⇒ False
```

> **自优化层被绑在「产品表现得差」这个条件上。**
> 产品越好，它越开不了 —— 而它本来是用来让产品变好的。

## 3. ★ 一个我自己差点犯的基线错

判据第一版我把 `BASELINE_WINDOW_HI` 设成 **0.37**（= oracle 样本的 0.2552+0.12），
而判据默认跑的是**名册标签**样本（0.5160+0.12 = 0.6360）。
⇒ 0.6360 ≥ 0.37 恒绿，**这道门从出生起就够不到**。

已订正为 0.63，绑死判据自己的默认样本。
**换样本就是换尺子。** [[baseline-must-be-the-same-kind-as-what-you-compare]]

## 4. 顺手撞到的一个真阻碍点

这是「**真的去用一次**」才会撞到的：

```
$ record_team_outcome.py --route-plan rp.json --delta-score 70 --task-slice small-product ...
Traceback (most recent call last):
  ...
FileNotFoundError: [Errno 2] No such file or directory: '70'
```

`--delta-score` 是 `type=Path`，而 `--help` 里**一个字的说明都没有**。
「delta-score」听起来就是个分数，第一次用的人几乎必然写数字。

**而本文件为「文件读得到但形状不对」精心写了 blocked JSON**（还配了两段注释解释为什么）。
⇒ **最可能被撞到的那条错路，恰恰是唯一没铺的那条。**

现在：

```json
{"status":"blocked","reason":"--delta-score 不是一个存在的文件：70 —— 这个参数要的是**文件路径**（由 `score_team_delta.py` 产出），不是数字或名字。**不写遥测**。"}
```

rc=2，并给 `--route-plan` / `--delta-score` 都补了 help（写明由哪个脚本产出）。

> **精心处理了少见的错误形状，而最常见的那种直接抛栈。**
> [[error-message-points-at-an-exit-that-isnt-there]]

## 5. 落了什么

`scripts/check_c_layer_is_reachable_for_a_working_product.py`（7 项自测）：

- ①② 钉住本件依赖的**两处源码事实**（ECE 阈值 0.12、预测量取自 marginal/base_score）
- ③★★ **正对照**：predicted==actual ⇒ ECE 0 ⇒ **必须**启用（不成立 ⇒ rc=4 未量，说明探针死了）
- ④★★★ **反对照**：0.24 vs 0.85 ⇒ **必须**启不了
- ⑥★ predicted 必须落在**远低于 1** 的区间 —— 它是排序分不是概率

调用方 6 项，其中 **★★★「跑完之后默认遥测文件的存在性不许变」** ——
判据自己会造遥测，**造在错的地方就会污染产品**。

**门一个都没改。**

## 6. 射程

- 两份样本都不是**真实用户提问**；真实分布下 predicted 的范围**没量过**。
  但结论对「窗口上沿」是单调的：**只要 predicted 是个 0–0.6 量级的排序分，
  70% 以上的真实成功率就永远过不了 ECE 0.12**。
- 「真实成功率是多少」**本身也没量过** —— 这里用 70/80/90% 只是「一个能用的产品该有的水平」，
  是**假设不是测量**。若真实成功率就是 30%，窗口是够得着的（但那本身是更坏的消息）。
