# **auto-gc 自己跑了，销毁了 76 个不可达提交**（2026-08-18，本会话内发生）

## 一句话

没人敲 `git gc`、没人敲 `git prune`。**Git 的 auto-gc 在本会话中自行触发并成功执行**，
销毁了 **76** 个不可达提交。可达面（分支/tag/HEAD/所有本地提交）**完好无损**。
这与铁律 3 记载的「丢过 2467 个提交」是**同一类事故**，只是这次规模小、且被当场量到。

## 时间线（全部有读数）

| | 读数 |
|---|---|
| 会话开始起，每条 git 命令都在警告 | `There are too many unreachable loose objects; run 'git prune' to remove them.` ★ **git 自己推荐的正是铁律 3 禁止的那条命令** |
| 我量的第一次 | 松散对象 **11347**｜in-pack 69419｜packs **3**｜**不可达提交 1360**（比 2 周老的 560） |
| 我设保护位 | `gc.pruneExpire=never`、`gc.worktreePruneExpire=never`（仅本仓） |
| 稍后再量 | 松散 **7619**｜in-pack **71058**｜packs **2**｜`.git/gc.log` **不见了** |
| 逐个核对 | gc 前记下的 1360 个：**仍在 1284｜已销毁 76** |

**松散↓3728、in-pack↑1639、packs 3→2、gc.log 消失** —— 这是 `git gc` 成功跑完的标准签名。
`gc.log` 是 gc 成功后自己删掉的，**不是我删的**。

## 为什么它会自己跑 —— `gc.log` 不是持久闸

    gc.auto      未设 ⇒ 默认 **6700** 个松散对象即触发（当时 11347，**早已越线**）
    gc.logExpiry 未设 ⇒ 默认 **1.day** —— **gc.log 只挡一天**，过期后 auto-gc 照跑
    gc.pruneExpire 未设 ⇒ 默认 **2.weeks.ago** ⇒ 比 2 周老的不可达对象**当场销毁**

⇒ 「仓里有 gc.log 所以 gc 不会跑」是**错的**。那道闸**一天就自己开了**。
  而每条 git 命令都在刷那句警告，**持续制造「把它删掉」的压力** ——
  删了 gc.log 只是让它早点跑，不删它也会跑。

★ 我自己的 ~12 次提交把松散对象推过阈值，**是我触发的**。

## 损失与未损失，分开说

**已销毁：76 个不可达提交**（读不出日期 —— 对象没了，`git log` 也就没了，
这正是「没有后悔药」的字面意思）。它们此前不被任何分支/tag/reflog 引用。

**完好：**

    git rev-list --all --not --remotes = **4234**（#125 记 4217，差 17 ＝ 本会话新提交）
    分支 6｜tag 5｜HEAD 正常｜git fsck 无损坏报告
    gc 前那 1360 个里 **1284 个仍读得到**

⇒ **没有任何可达提交丢失**；丢的全部在「不可达」那一档。
  但「不可达」不等于「不要」—— #125 说本机有 4165 个备份/快照/tag 类提交，
  它们**是否有一部分正靠不可达对象活着**，只有 Owner 说得清。

## 已做的防线（只会阻止删除，不会造成删除）

    git config --local gc.pruneExpire never
    git config --local gc.worktreePruneExpire never

★ 这两条**只能阻止 gc 删东西**，本身删不掉任何东西，因此我判定它属清理不属决定。
★★ 验它生效的正确方法**不是** `git prune -n` —— 那条**只管松散对象**，
   而抽 400 个不可达提交实测 **399 个在包里、只有 1 个是松散的**。
   包里的不可达对象靠 `git gc` 的 repack 掉，`prune` 够不着。
   **我第一次就是拿 `git prune -n` 去验的，还写了一句「↑ 空＝生效」的无条件结论
   —— 而命令那次明明印出了对象。** 订正在此。

## 要 Owner 定的

1. **这 76 个要不要追**？备份/快照仓（#125 提到的另外几处）里可能有副本，
   但那要 Owner 说哪一处是权威备份。
2. **`gc.pruneExpire=never` 留不留**？留着的代价是不可达对象永不回收（现 pack 955 MB）。
   撤掉的代价是下一次 auto-gc 会把现在这 **2149** 个不可达提交里比 2 周老的清掉。
3. **那句警告要不要治本**？治本＝让不可达对象变可达（给它们打 tag/建分支），
   或明确宣布它们可弃。**我不替你选，两个方向都不可逆。**

## 可复算

```bash
git config --get gc.pruneExpire            # 期望 never
git count-objects -v                       # 松散/in-pack/packs
git fsck --unreachable --no-progress | awk '$2=="commit"' | wc -l
git rev-list --all --not --remotes | wc -l # 可达面完好性的要害数
# 核对某一批 SHA 还在不在（**用 --batch-check，别逐个起进程**）
git cat-file --batch-check < 某份sha清单.txt | grep -c missing
```

## ★★★ 追记（同日，晚些）：**保护位被真实事件验过了，不是只写在注释里**

设完 `gc.pruneExpire=never` 之后又提交了若干次，`gc.log` **再次出现**
（＝**又有一次 auto-gc 尝试**）。拿上一次 gc 后**幸存的那 1284 个** SHA 逐个复核：

    git cat-file --batch-check < still.txt | grep -c missing   →  **0**

    这一轮不可达提交总数 2149 → **2157**（涨了，没降）
    可达面 git rev-list --all --not --remotes = **4238**（继续随本会话提交上涨）

⇒ **第一次 gc（无保护位）销毁 76 个；第二次 gc（有保护位）销毁 0 个。**
  这不是「注释声称有守卫」，是**同一台机器、同一个仓、同一类事件的前后对照**。
  [[a-comment-claiming-a-guard-is-not-a-guard]] 要求的正是这种证据。

★ 附带确认一件事：**警告不会消失**。「too many unreachable loose objects」
  只有把那些对象**删掉**才会平息，而那正是我们不许做的事。
  ⇒ **这条警告从此是常态，不是待办**。谁看见它想「治一下」，请先读上面那 76 个。
