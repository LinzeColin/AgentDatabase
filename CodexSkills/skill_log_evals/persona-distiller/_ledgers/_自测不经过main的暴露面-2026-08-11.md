# 自测不经过 `main()` 的暴露面 —— **量到的与量不到的**

日期：2026-08-11。起因：我给 `build_blind_payload.py` 加开关时写了 `args.balanced_positions`，
而 main 的局部变量叫 `a`。**`py_compile` 绿、`ast.parse` 绿、`--self-test` 全过，
而工具每次真调用必崩**，坏版本还提交了一次（`cbd69efc`，已由 `bc43023c` 修复）。

抓到它的不是任何一道自测，是**我坚持真跑一次命令行**。

## 一、暴露面：94 / 100

`scripts/` 下**有 `main()` 且有自测**的文件 100 件，
其中**自测完全不经过 `main()` 的 94 件**（判据：自测函数体里既不调用 `main(`，
也不以 `subprocess` 跑 `__file__`）。

→ 这 94 件里，任何一个只存在于 `main()` 正文的名字错、参数名错、路径拼接错，
**自测一律看不见**。

## 二、★★★ 我跑了一次全量扫，而**那个数说明不了我想让它说明的事**

扫法：对 123 件有 `main()` 的文件**空参数直接调用**，看有没有抛出代码类异常。

    结果：正常 123 件（含 1 件超时）｜抛代码类异常 **0 件**

**这个 0 不能读成「没有同类 bug」。** 空参数时 `workspace` 之类是 `None`，
工具在参数校验处就早退了——**根本走不到 main 的正文**，
而我那个 bug 正在正文里（`assign(...)` 那一行，在读完夹具之后）。

★ 也就是说：这次扫描只证明了**导入期与 argparse 期没坏**，
**对 main 正文一无所知**。[[samples-cannot-support-universal-claims]]、
[[a-checker-nothing-calls-is-not-a-checker]] 第五批「检查不经过被保证之物」。

**我差一点把「0 件」当成「全库干净」写出去。**

## 三、唯一真能覆盖的做法，以及它的代价

要覆盖 main 正文，必须**每件工具配一份最小夹具、走命令行真跑一遍**。
`build_blind_payload.py` 已经这样做了（临时目录里造 4 题夹具，
以 默认 / `--balanced-positions` / `--key-dir` 三种方式各调一次，断言 stderr 无 Traceback）；
★ 变异实测：把 `a.` 改回 `args.`，**三条冒烟全部变红**。

代价：**94 件各需要一份夹具**。夹具的形状按工具分四类
（吃工作区的、吃单文件的、吃目录对的、吃全库根的），不是一个模板能套完的。

## 四、处置

- **不宣称「全库已核」**。已核的只有 1 件（`build_blind_payload.py`）。
- 本条记为**已量清未修**，规模 94 件、按类分四组。
- ★ 下次任何一件工具**新增或修改 `main()` 里的代码**时，**当场补一条命令行冒烟**——
  按发现升版、不攒批（[[iterate-per-finding-not-per-batch]]）。
  攒成「94 件一起补」的批量任务，按本项目的历史就是**永远不做**。
