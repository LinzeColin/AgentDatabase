# 「真的去用一次」—— 一小时里撞出~~四个~~**六个**缺陷，没有一个是读代码读出来的

> ★ **标题订正（同日）**：写下「四个」之后，同一轮又撞出两个（⑤⑥）。
> **「只有 N 个」这类计数断言，写之前先问「我还会不会接着找」。**
> [[claims-my-own-next-delivery-falsifies]]

**日期**：2026-08-18　**包**：v0.0.0.43 → **v0.0.0.47**（四次升版）

今天前半天我在**读代码**：量路由、量准入、量分派、量分歧、量体量。
后半天换了个动作：**把每个脚本当第一次用的人那样，真的敲一遍命令。**

**六个缺陷，全部来自后半天。**

---

## ① `--delta-score 70` ⇒ 未捕获的 traceback

```
FileNotFoundError: [Errno 2] No such file or directory: '70'
```

`--delta-score` 是 `type=Path`，而 `--help` 里**一个字的说明都没有**。
「delta-score」听起来就是个分数 —— 第一次用的人几乎必然写数字。

**而这个文件为「文件读得到但形状不对」精心写了 blocked JSON，还配了两段注释解释为什么。**

> ⇒ **精心处理了少见的错误形状，而最常见的那种直接抛栈。**

改：读不到文件走同一条 blocked 出口（rc=2），两个参数都补 help（写明由哪个脚本产出）。

## ② 用户看的那张卡片把两条实打实的贡献静默丢掉

`material_expert_contributions: []` —— 而我明明喂了两条。

真因：筛选要求每行有 `decision_influence > 0` 或 `artifact_owned`，
而这两个字段在 **SKILL.md 与 references/*.md 里出现 0 次**
（`member_contributions` 本身写在 SKILL.md:200）。

> ⇒ **文档叫你填 A，代码按你没听说过的 B 来筛。**
> 卡片上的 `[]` 与「这支队伍没有做出实质贡献」**一模一样**。

★ 这是**同一形状的第四处**。该文件对前三处守得极好（result 传错／delta-score 传错／
六区段全缺，各配注释 + blocked）。**前三处守的是「你拿错了文件」，第四处是
「你拿对了文件但填不全你没听说过的字段」—— 后者才是照着文档做事的人真正会撞到的。**

改：**筛选规则一个字没改**（改它会改变卡片的判断），改成**把丢掉的说出来**。

## ③ 第四处版本声明位漂了 13 个版本

跑 `audit_persona_fleet_for_team.py`（它**写盘**）⇒ 立刻查 diff：

    准入数据逐字节没变，只有 "source_generator_version": "v0.0.0.32" → "v0.0.0.45"

而版本绑定门只管三处，`expert-fleet-admission.json` 在它里面出现 **0 次**。

> **没人比对的一处声明位，就是下一个「7 个版本号」的起点。**
> 人物侧 v0.0.0.13 那次正是这么来的（8 处声明位只比了 2 处）。

改：绑定门加第四处；文件不在时**不报错**（那是「没跑过 fleet 审计」不是漂移）。
★★★ 在**真树**上做过反例：手工改回 v0.0.0.32 ⇒ 确实判红；
再**用真的生成器重跑**复原（不是手工改回去）。

## ④ 四份运行产物没有一份说得出「是哪个版本跑的」

跑**编排器**（我一整天都在直调每一步 —— 正是「守卫加在编排器上会被绕过」的形状）。
它跑得通，还多产一份 `run-receipt.json`。**收据不带版本号。**

逐份查：四份产物含 version 的顶层键全都只有 `schema_version`；
文中的 `v0.0.0.1` 是**人物交付包**的版本，不是本 skill 的。

> ⇒ **仓内产物有出身，运行产物没有** ——
> 而运行产物才是宿主真去执行、用户出了问题会拿来对质的那一份。

改：收据加 `generator_version`。读不到写 `None`，**不写 `"unknown"`**。

## ⑤ `backfill --apply` 会把 97 份记录一律盖成同一个版本

跑 `backfill_distilled_with.py`（默认 dry-run，设计是对的）。它说「需更新 **97** 份」，
全归到 `v0.0.0.154 / git-first-commit`。

**停下来问了一句**：97 个人是几周里陆续蒸的，第一次提交时的版本不可能全是同一个。
逐一查 git ⇒ **「首次落盘提交」102 / 102 = 100% 是同一个提交**（2026-08-14）。
那不是「同一天蒸出来」，是**整棵树那天才进的 git**。

> ⇒ 归因方法本身是对的，**但在这棵树上它什么也看不见**。
> **一个统一而错误的出处，比没有出处更坏** —— 后者是「不知道」，前者是「知道错了」，
> 还配着一个听起来很权威的 `source: git-first-commit`。

改：两趟（先算后写）＋ 分布每次都印 ＋ 退化时 `--apply` 拦下要 `--anyway '<理由>'`。
**没有跑过 `--apply`**，97 份记录一个字节没动。

## ⑥ `relative_to` 在任何路径带软链的机器上直接抛异常

这一个**不是我读出来的，是我写的测试炸出来的**：
`git rev-parse --show-toplevel` 返回**已解析软链**的路径（macOS `/var → /private/var`），
而 `record_path` 常是未解析的 ⇒ `relative_to` 抛 `ValueError`。

改：两边都先 `realpath`。[[path-prefix-checks-need-realpath]]

> ★ 值得单记一句：**⑥ 是测试帮我找到的，不是我帮测试找到的。**
> 我造那棵临时 git 树只是为了给 ⑤ 的守卫做正对照 —— 结果它先炸出了产品的一个真 bug。

## 改的过程里我自己连撞三次，全部当场抓到

1. 变量名写成 `registry_root`，作用域里叫 `root` ⇒ 编排器 **rc=1**。
   （**读 traceback 的 `NameError`，不猜**。）
2. 断言 `assertNotIn('"unknown"', src)` **被我自己写的那句注释绊倒** ——
   注释里正写着「不写 `"unknown"`」。
   **判据要 key 在代码上，不要 key 在措辞上** ⇒ 用 `tokenize` 剥注释。
   [[checkers-must-key-on-a-closed-set-not-on-wording]]
3. 剥完注释，tokenize 把 token 间空白也吃了（`_gen = None` → `_gen=None`）
   ⇒ 第二条断言又假红 ⇒ 两边都去空白再比。**断言不许因为排版而红。**

## 这一条本身的教训

**读代码找得到「写错了什么」，用一次才找得到「用起来是什么感觉」。**

六个缺陷的共同形状是同一个：

> **产品对「我预料到的错」守得很好，对「照着文档做事的人真会做的事」没有守。**

- ① 守住了「文件形状不对」，没守「参数根本不是文件」
- ② 守住了「文档传错了」，没守「文档传对了但字段没填全」
- ③ 守住了三处版本位，没守第四处
- ④ 仓内产物记了出身，运行产物没记
- ⑤ 守住了「归因不到就标 unknown」，没守「归因到了但全归到同一个值」
- ⑥ 守住了正常路径，没守**软链**路径

**每一个都不是「忘了写代码」，是「守卫画的圈比真实的使用面小一圈」。**
