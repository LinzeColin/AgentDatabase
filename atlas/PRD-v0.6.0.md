## 1. 已经修掉的四个假数字（本轮已上线，构成下面所有讨论的新基线）

| 版本 | 修的是什么 | 影响面 |
|---|---|---|
| **v0.5.2** | cron 拿不到 `gh` 和 `node`，定时任务会**静默跑出半份数据** | 首次触发前堵住 |
| **v0.5.3** | 「被问过 738 次」实为**一天之内的一批图片标注扇出**；`repeats` 25 组里 21 组 `days<=1` | 该数字已写进 agent 契约、分发到 5 个入口，并作为 v0.5.0 Champion 的头号证据 |
| **v0.5.4** | 30 个项目简报**全部**「常见话题：—」（`sediment` 读的抽取产物里根本没有 `topics` 字段）；「每场 213 次报错」数的是**词频** | 每个 agent 读到的都是死字段 |
| **v0.5.5** | **所有 token 绝对量虚高 2.3 倍** —— 一个 API 响应在 JSONL 里被拆成多行，每行都带完整 `usage` | 站上每一个 token 数字 |

### v0.5.5 值得单独说：它为什么能藏这么久

【实测】全语料 1,528 个 transcript：322,284 条 `usage` 记录只对应 **130,138 个不同的 `message.id`**。

修前 → 修后：

| | 修前 | 修后 | 虚高 |
|---|---:|---:|---:|
| 读进去的（含缓存） | 141,514,921,534 | **62,326,715,383** | 2.27× |
| 模型写出来的 | 392,929,062 | **150,880,732** | 2.60× |
| 每条提交摊到的新 token | 730,326 | **420,631** | 1.74× |
| 「最贵的一天」 | 130.8 亿 | **38.2 亿** | 3.43× |
| **缓存命中率** | 0.998544 | **0.996694** | **1.002×** |

**最后一行是答案**：四类 token 一起虚高，比值几乎不动。而命中率恰恰是这块最常被看的数。
**只看比值的人永远发现不了分子分母同时错了。**

更麻烦的是虚高**不均匀**：一轮里并行工具调用越多虚高越狠，单场 1×–4.99× ——
**最 agentic 的会话虚高最严重**，所以按天/周/来源的排序都被非均匀扭曲过。

> **这一条给 v0.6.0 定了基调**：先把口径修对，再谈加指标。
> 不修 P0 就上新指标，只是把错数换成美元单位。

## 2. 四路调研各自最硬的一条

### 2.1 AEI —— 你对齐的那个东西自己一直在变

【官方】AEI 至今发布 6 版（2025-02 / 2025-03 / 2025-09 / 2026-01 / 2026-03 / 2026-06）。三条被它自己推翻的结论：

1. **automation/augmentation 的比值 16 个月内翻了两次方向**：
   57/43 → 57/43 → **49.1/47（automation 首次反超）** → **45/52（又反超回去）**。
   → 把它做成「你的自动化率是 X%」这种单点展示是误导的；它只有在同口径时间序列里才有意义。
2. **「越资深越倾向自动化」是错的**（v5, 2026-03-24 明确推翻自己 2025 年的假设）。
3. **AEI 把自己的生产率估计砍了一半**：1.8pp → 1.0–1.2pp，理由是乘上了 task success rate ——
   「如果工人必须验证 AI 输出，raw speedup 就高估了实际收益」。

【官方】还有一条对本项目最要紧：AEI 的**隐私下限**是「某任务至少 15 段对话 **且** 跨 5 个不同账号」，
低于门槛的任务**直接不进分析，不是记成 0**。

【第三方·最该看的一条】**METR 随机对照实验**（arXiv:2507.09089）：
资深开发者在**自己熟悉的成熟仓**上用 AI，实测**慢了 19%**；而当事人自评**快了 20%** ——
**差 39 个百分点**。调研者逐字核过原文：METR 2026-02-24 改了实验设计但**没有撤回结论**
（网上流传的「METR 承认致命缺陷」是假的）。

> **这条为什么对本项目致命**：Memory Atlas 测的恰好就是这个最真实的一端 ——
> 一个资深的人，在自己的仓上，重度用 agent。
> **任何「你省了 X 小时」的展示，方向都可能是反的。**

> 而本机的另一处 AEI 实现（`OpenAIDatabase/scripts/memory_atlas_private/analytics.py`）
> 把 **91.22%** 分不出来的事件记成一个叫 `mixed_or_unknown` 的桶，
> 然后和 automation/augmentation 并列展示成三个百分比。
> **这在数学上是把「没测出来」当成了「测出来是第三类」。**

### 2.2 token —— 78% 的账单在你看不见的那一栏

【实测】本机账单结构（按已核实单价折算）：**cache read 占 78.15%**。

而 `aei.py` 的成本口径是 `cost_tokens = tok_in + tok_out` ——
**排除了 cache read + write，也就是 88.3% 的钱**。
代码注释里的单价判断是对的（cache read 是 0.1×，官方已核实），但结论反了：
**量比是 860:1**，0.1 的单价乘 860 倍的量，仍然是大头。

【实测】`cache_write` 在整个 `web/` 目录里 grep 零命中 —— **单价最高的那类输入 token 从不显示**。

【实测】**94.5% 的 token 记在了错误的日子上**：会话按 `start` 日归集，最极端一场跨 **24 天 16 小时**、
独占其 start 日的 99.7%。→ 「某天 130 亿 token、0 次提交」这条债务卡**极可能就是归集假象**。

【实测·反直觉】**上下文压缩比不压更贵**：$0.11 → $0.24/轮（+118%），记忆召回 92–100% 掉到 38%。
机制是摘要要重发全量历史 + 前缀重写击穿缓存。【官方】Anthropic 把 compaction 列在「会毁 cache 的动作」里。
**正确做法是开新会话，不是压缩。**

【实测·合规】**SCNet Token Plan 明令禁止 API 脚本化/批量调用** ——
3,818 场扇出会话若走这条线，是合规风险不只是成本问题。

【实测】**DeepSeek 2026-08-16 把缓存命中档涨了 6 倍**，且命中率越高吃亏越大
（同负载账单变 2.7 倍；命中率为 0 反而只涨 1.5 倍）。

### 2.3 agent 记忆 —— 现有的零模型路线不是妥协，是更对的选择

【第三方】Letta 实测：**「文件系统 + grep」在 LoCoMo 上 74.0%，打赢 mem0 的 68.5%。**

【第三方】而所有 memory benchmark 分数都不可信：LoCoMo 全塞 26k token 的 baseline 就 72.9 分；
独立审计发现 **6.4% 标准答案是错的**；judge 会放行 **62.81%** 的错答案
（诚实上限只有 ~93.6%，而某厂商宣称 95.23%）。Zep 同一个数字公开摆动过 58.44 / 65.99 / 75.14 / 84 四个值。

【实测】6 个成熟项目（mem0、Letta、Graphiti、cognee、LangMem、MemOS）**写入端全部强依赖 LLM，
无一有零模型模式** —— Graphiti 连手工插三元组都要过一遍 LLM。按「运行期零模型」红线**全部出局**。

【实测·最关键】**现有流水线沉淀的是「问题被问了几次」，不是「答案是什么」。**
`to_markdown()` 五个小节全是统计，唯一的行动建议是一句固定文案。
**所以「写下来了还找不到」的根因是：答案从未被写下。**

【实测·反直觉】**prefix-26 判重其实够用**（近重复召回 91.7%、跨天 85.1%）——
「换语义检索能大幅提升召回」的直觉是**错的**，不该往那投入。

【官方】Anthropic 的措辞很硬：
「**Bloated CLAUDE.md files cause Claude to ignore your actual instructions!**」
「**If Claude keeps doing something you don't want despite having a rule against it,
the file is probably too long and the rule is getting lost.**」
→ 而我分发的契约块是 **116 行**，在 `~/.kimi-code/AGENTS.md` 里占 **97%**、`~/.claude/CLAUDE.md` 占 **76%**。

### 2.4 成果转化 —— 缺的不是框架，是「对外」那一列

【实测】读完 `compound.py` 的结论：**这套漏斗比调研找到的大多数公开框架更严格** ——
它连「部署成功」都不算 OUTCOME，`_evidence_ceiling()` 用代码强制只降不升。
**缺的不是框架，是 `economic` 那一列的数据入口。**

【实测】现有 `opportunity_block()` 的四类素材**全部是对内的**。
「造 → 交」这段能测（`shipped` 字段），**「交 → 换到钱」这段一条信号都没有**。

诊断清单里 8 个问题，**第 3、4、6、7、8 条现在都取不到 —— 而这五条恰好全部是「对外」的**：

3. 我向多少人开过价？被拒了几次？理由是什么？
4. 有没有人为了解决这个问题，在过去 12 个月里花过钱？
6. 这个东西如果今天消失，谁会来找我？
7. 我的分发渠道是什么？它现在有多少人？
8. 距离第一美元还差几个动作？

**这就是 10:5:1 里从 5 到 1 的那一段。**

【有分母】而且「在 0 用户阶段，所有『率』都是假的，只有『数』是真的」：
- 5% 基线要检出 20% 相对提升，需 **8,158–15,000 访客/变体**
- Sean Ellis PMF 测试需 **40–100 份**活跃用户回答
- → `compound.py` 的漏斗**计数**（每档几条候选）恰好是「数」不是「率」，**这个选择是对的，保留**。

## 3. v0.6.0 提案

依赖顺序是硬的：**P0 不做完，P1 的结果就是把错数换个单位。**

### P0 —— 成本口径修正（不做这条，下面全部无意义）

#### P0-1 `cost_tokens` 要把 cache 算进去

**现状**：`aei.py` 的 `cost_tokens = tok_in + tok_out`，覆盖 **11.7%** 的账单。

**改成**：价格加权 token（base-input-equivalent）
```
BIE = in×1.0 + cache_read×r + cache_write×w + out×(out价/in价)
```
倍数按 provider 取，**单价表版本化并记抓取日期**。

**为什么不直接用美元**：单价会变（本轮就抓到两处刚变过）。历史数据必须用**当时**的价重算，
不能用今天的价重算历史。BIE 是无量纲的，跨时间可比；美元留给「当期账单」那一栏。

**⚠️ 失效条件（必须写进页面）**：
- 跨 provider 加总不成立（DeepSeek 的 r=0.032 不是 0.1，off-peak 再砍半）
- **Gemini 显式缓存装不进这个公式** —— 它按「租金 × 小时」计费，与 token 量正交
- **跨 tokenizer 版本不可比**：Claude 4.7+ 换了 tokenizer，同样文本多约 30% token，
  BIE 跨版本比较会把 tokenizer 变更读成用量增长

**验收**：站上「成本」一栏的覆盖率从 11.7% → **≥95%**；`cache_write` 首次出现在页面上。
**负控**：构造一个只有 cache_read 没有 fresh input 的会话 → 成本必须 >0（现在是 0）。

#### P0-2 token 按小时摊到真实日期，不按 start 日整块归集

**现状**【实测】：**94.5%** 的 token 记在错误的日子上；最极端一场跨 24 天 16 小时。

**改成**：会话已有 `hours` 桶（`hour_buckets()`），按桶把 token 线性摊到各日。

**验收**：重算后「最贵的一天」若变化 >20%，说明归集假象是真的 ——
**同时公布新旧对照**，不许悄悄换掉。
**负控**：构造一场跨 3 天的会话 → 三天各拿到一部分，且三者之和 = 原值。

#### P0-3 承认扇出成本不可观测，别再假装它是 0

**现状**【实测】：Claude Code 子 agent 的 `usage` **根本不在父会话文件里**。
（调研者原以为走 `isSidechain:true`，实测该字段 6,718 次全是 `false` —— 他把这个推翻记了下来。）

**改成**：在「Token 与栈」页新增一行 **`扇出成本：说不准`**，并说明为什么。

**为什么这是个功能不是认怂**：3,818 场扇出会话的成本现在**完全没进任何一个数**。
不写出来，「每条提交摊到 42 万 token」看起来就是全部真相。
**这条零代码成本，只需要一行诚实的文案 + 一个 `state` 字段。**

### P1 —— 把「对外」这一列接进来（这是 Owner 真正卡住的地方）

#### P1-1 对外动作计数（最小可行，确定性派生）

**做什么**：新增一个确定性信号 —— **「过去 30 天，有没有一个动作的收件人不是我自己」**。

**怎么派生（零模型）**：从会话主题与工具调用里认这些确定性痕迹：
- `gh pr create` / `gh release create` 指向**非自己的仓**
- 发帖/发布类主题词命中（现有 `TOPICS` 表已有「部署上线」，需新增「对外发布」一类）
- 邮件/消息类工具调用
- **报价/合同/发票**类关键词

**输出**：转化页新增一块「对外动作」，四态：`本周 N 次 / 本月 N 次 / 从来没有 / 说不准`。

**为什么这条排第一**：调研的排序判断是
「第 3 名 · 用会话数据本身做内容 —— **缺的那一步是一次公开发布，而他发出去的次数是 0**」。
**一个恒为 0 的计数器，比十个漂亮的内部指标有用** —— 它是唯一能让人看见「我还没开始卖」的东西。

**验收**：这个数现在应该是 **0 或接近 0**。如果它一上来就很大，**说明判据写错了，不是说明干得好**。
**负控**：把判据里的关键词删空 → 必须变成「说不准」，不能变成 0。

#### P1-2 用真实的 `is_error` 替换词频

**现状**【实测】：`extract.py` 数的是 `joined.lower().count("error")`。
一段贴进来的日志能一次贡献上百次。v0.5.4 已经把**标签**改诚实了，但口径还是词频。

**改成**：各家日志里的结构化失败字段
（Claude Code 的 `is_error:true`；【实测】抽样 120 个会话文件 **51% 命中**）。

**代价**：`PARSER_FINGERPRINT` 变化 → 全量重解一次（实测 69.5 秒）。

**验收**：新旧两个口径**同时保留一段时间**并给对照；差异倍数公布。
**负控**：构造一个正文里写满 "error" 但零工具失败的会话 → 新口径必须是 0。

#### P1-3 ROI 的分母从 commit 换成 merged PR

**现状**：`roi` 只用了 `commits`。而 `delivery_block` **已经在采 `prs` / `merged` 了**
（`metrics.py`），只是没用上 —— **这是零成本的改进**。

**为什么**：commit 粒度极不均匀（1 行 typo 和 2000 行重构同为 1 commit），
且**任何按 commit 数考核的口径，最终都会得到更多、更小的 commit**。
merged PR 有 review 边界、粒度均匀，还能区分「合了」和「提了没合」。

**验收**：两个分母并列显示，不替换。

### P2 —— 沉淀：从「给地址」改成「提问那一刻给命中项」

#### P2-1 `UserPromptSubmit` 钩子 + 本地 BM25 索引

**现状的失效点**【实测】：现在注入的只是一个 `gh api` 地址，不是内容。
**本次会话实测转化率就是 0** —— 调研 agent 全程没执行那条命令，是翻文件系统才偶然读到 brief。

**做什么**：
- 离线派生 `brief_index.jsonl`：每行 `{terms:[…], line:"一句话", pointers:[…], first_seen, last_seen, n}`。
  `terms` 取**字面词元**：路径片段、仓名、命令名、错误码、专有名词、中文 2–4 字切片。
- 运行期挂 `UserPromptSubmit` 钩子，用 **Python 标准库做 BM25 字面打分**，
  命中就注入 **≤3 条、每条 ≤2 行**；无命中注入空串。

**为什么不需要模型**：
- BM25 是算术不是推理。【厂商但可核】Anthropic 实测 contextual embeddings **+ BM25**
  把检索失败率 5.7% → 2.9%（−49%），并明确指出**精确标识符上字面匹配优于语义 embedding**
  —— 而本项目的沉淀内容几乎全是路径、命令、错误码。
- 【官方】钩子的 context 成本「**Zero, unless the hook returns output**」，
  触发「**Always fires on its event; the trigger is guaranteed**」——**不依赖模型判断要不要读**。

**⚠️ 验收指标的选择极其重要**：
【实测】「注入命中率」对扇出剔除阈值**极度敏感**：T=5 → 4.6%；T=10 → 14.0%；T=20 → 21.3%；T=50 → 33.2%。
**必须先把剔除规则写死并公布，再谈命中率** —— 否则这个指标可以随便调到好看。

**主指标应该是**：**30 天内新增的跨天重复组数下降**（当前 10 组，首末间隔中位 4 天）。
这个指标不受扇出定义影响。

**负控（必须单独跑）**：
1. 语料里从未出现过的问题 → **必须 0 注入**（防「什么都命中」的假绿）
2. 已知重复问题 → 必须命中且给出正确指针
3. 删掉索引文件 → 钩子必须**静默成功**（不能阻断提问）并在日志留痕

**⚠️ 不要用「省了多少 token」当指标**。【第三方】140 次配对实测：
cached input 占 token 的 96.46%、占成本的 63.91%，模型输出只占 token 的 0.38% ——
针对「注入体积」的优化映射到总成本上不足 1%。
**注入的价值来自少返工一次，不来自省下几百 token。**

#### P2-2 沉淀「答案的指针」，不是「问题的频次」

在 `repeats` 每组补三个**可确定性派生**的字段（全部来自工具调用的结构化记录）：
- `artifacts`：该组最后一次会话里 Write/Edit 触碰过的文件路径
- `commands`：成功执行过的 Bash 命令（去重取 top3）
- `commits`：当天该仓的 commit hash（`github.json` 已在拉）

产出一行：`问过 N 次 → 最后一次落在 <path>，用的是 <cmd>，commit <hash>`。
**不写摘要、不改写原话 —— 只给指针。**

【第三方】依据：Zep 在 LongMemEval 的 `single-session-assistant` 上比 full-context **低 14.2 个点**
—— 压缩改写会牺牲「精确复述当时的东西」。**保留指针优于保留摘要。**

**验收**：指针可核率 ≥95%（自动校验路径/commit 存在）；覆盖率 ≥80%。
**负控**：构造一条「会话里什么文件都没改」的重复组 → 必须产出空指针并如实标「没有产物」，**不许编路径**。

#### P2-3 契约瘦身：116 行 → 25 行

【官方】Anthropic：「Bloated CLAUDE.md files cause Claude to ignore your actual instructions!」
【实测】契约块 116 行，占 `~/.kimi-code/AGENTS.md` 的 **97%**。

**改成**：常驻只留 25 行（地址 + 四条硬规矩 + 一句「细则见 X」），
其余移到 `paths:` 规则文件与 skill，按需加载。

**验收**：常驻块 ≤25 行；**且**归档时仍然产出事件（用真实会话验，不是看行数）。

### P3 —— AEI 重做：先拆总体，再谈百分比

#### P3-1 把「人」和「机器」拆成两个总体

【官方】AEI 从 v3 起就把 Claude.ai 与 1P API 分开报，因为两者 automation 率差得离谱
（**49.1% vs 77%**）。混在一起的比值没有含义。

本机对应切分（判定规则已实测可用，零模型）：

| 总体 | 判定 | 回答什么 |
|---|---|---|
| **H 人在对话** | 其余 | 这个人怎么工作 |
| **F agent 扇出** | 同来源同小时 ≥15 场 | 这套系统怎么跑 |
| **B 批处理** | 无用户发言／单轮机器指令／前 80 字重复 ≥5 次 | 同上 |

**注意**：v0.5.3 已经证明现有的 F/B 判定**会漏**（评委面板每条提示词带不同人名）。
所以这一步要**同时**引入 v0.5.3 的速率闸作为第三条判据。

#### P3-2 删掉 6 个在单人数据上是伪科学的指标

| 指标 | 为什么删 |
|---|---|
| 职业任务覆盖率 | 分母是「某职业的全部任务」，是跨人构造的总体。硬算出来的分母由分子决定，**指标恒真** |
| 工资分布 inverted-U / task value | 需要跨职业工资分布，单人只有一个点 |
| 劳动生产率 pp | Hulten 定理三个输入全缺（无工资份额、无任务时间权重、无可信反事实耗时） |
| AUI / Gini（原义） | 测的是人与人之间的不平等，单人无跨人分布 |
| 「今年省了 41.95 小时」 | 【第三方】METR 实测：即便让当事人**亲自估**，也有 **+40pp 的系统性高估**。用常数假设算只会更差 |
| `automation_ratio = 0.7273` | 11 个样本输出到小数点后 4 位 —— **精度冒充了确定性** |

**替代**（诚实版）：
- Gini 数学对象保留，但**改名改叙事**为「跨项目注意力集中度」，并写明「这不是 AEI 的 Gini」
- AUI 改成「**项目注意力偏离度 = 该项目会话份额 ÷ 该项目代码份额**」——
  分母是外生可测量，不会自证。**但仍会骗人**：新建仓代码少却必须投入注意力，恒 >1，**必须按仓龄分层**

#### P3-3 「可判定率」升为一级指标

【官方】AEI 的隐私下限（≥15 对话且 ≥5 账号）事实上起「有效样本门槛」的作用 ——
**低于门槛的直接不进分析，不是记成 0**。

**改成**：分母只取可判定集合，**同时把「可判定率」单独露出来**。
现在 `domains_unclassified` 已经在做一半，要扩展到所有分类维度。

## 3.5 需要你拍板的一个 A/B（不做选择就是选了第三种最差的）

【官方】SPACE 框架原文其实**允许你测自己**：
「Individual-level productivity analysis, however, may be insightful for developers」——
它禁止的是**组织拿个人数据做评价**，不是禁止个人自测。

但按 SPACE 自己的规则，**现在这一版不合格**：
- 五个维度（Satisfaction / Performance / Activity / Communication / Efficiency）里，
  **只有 Activity 一个维度有数据**
- **零个感知类指标**
- 而 **Activity 正是 SPACE 原文点名「绝不能单独使用」的那一个**

而本仓有「零 Agent 零 Token」铁律，**感知数据无法从日志派生**。所以只有两条路：

| 选项 | 做什么 | 代价 | 得到什么 |
|---|---|---|---|
| **A** | 加一个**每天 10 秒的自评滑块**（今天顺不顺、返工多不多）。纯本地写文件，**不调模型、不违反铁律** | 你每天 10 秒的习惯 | SPACE 合格；且有了唯一能校准 METR 那 39pp 偏差的东西 |
| **B** | 不加。但**产品里从此不再出现「生产力」「省了多少」这类词** | 少一个叙事 | 诚实 |

**第三种（既不加、又继续说生产力）是另一种假数据。** 这一条我不替你选。

## 4. 明确不做的（附理由）

| 不做 | 理由 |
|---|---|
| **上下文压缩 / LLMLingua** | 【第三方】ECIR 2026（30,000 queries）：vLLM 下短 prompt **净变慢**，商业 API 常 **<0.5×**。【第三方】NAACL 2025：agent 任务只压 **1.1×** 就掉 **76%**，3.3× 全灭。本项目的负载正是 agent + 结构化输出 |
| **换语义检索 / embedding** | 【实测】prefix-26 判重召回已 91.7%，且沉淀内容以路径/命令/错误码为主，**字面匹配本就优于语义** |
| **引入 mem0 / Letta / Zep** | 【实测】6 个项目写入端**全部强依赖 LLM**，违反「运行期零模型」红线；且【第三方】Letta 自测「文件系统+grep」反而赢 |
| **上下文自动压缩（compaction）** | 【实测】比不压**贵 118%**，召回 92–100% → 38%。正确做法是**开新会话** |
| **给自己定一个假设时薪来算「省了多少钱」** | 见 P3-2 的 METR 证据。要做只能显式标成假设值，且不进任何总量 |
| **A/B 测试 / PMF 调查 / 留存曲线** | 【有分母】0 用户阶段样本量差 3–4 个数量级，产生的是噪声不是信号 |
| **卖 prompt / Claude Skill / MCP server 的指标** | 【查不到】三个赛道要么在缩（PromptBase 月访问 −13.6%），要么**连一笔公开成交额都查不到** |

## 6. 这份 PRD 自己的局限

- **WebSearch 配额在调研中途用完**（200/200），后段只能靠 WebFetch。
- **中文一手数据严重不足**：知乎/CSDN/公众号/微博/小红书正文基本抓不到（403/521/antispider/登录墙）。
  变现方向只拿到 **2 个够硬的中文案例**；掘金小册/极客时间的作者收入分成**确实查不到**。
  agent 记忆方向判定「该主题 80~90% 是复述官方文档或厂商稿」。
- **AEI 方向的「现有实现差距表」审计错了对象**：主树的 sparse-checkout 排除了 `atlas/`，
  调研 agent 找不到 `aei.py`，转而审计了 `OpenAIDatabase/` 下另外两处 AEI 实现。
  **那一节不可用**；但它顺带发现了一件更重要的事 —— 本机存在**两套并行且结论矛盾**的 AEI 分析
  （atlas 说 automation 63%，另一套说 4.25% 且 91% 未分类）。**这本身是「两条事实链」，应当合并或废掉一条。**
- 本 PRD 引用的所有单价均带抓取日期，**它们会变**。
