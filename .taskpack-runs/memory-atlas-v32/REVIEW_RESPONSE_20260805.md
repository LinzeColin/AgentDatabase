# 对 v0.0.0.31 / v0.0.0.32 复审的逐条回应

复审裁决 **FAIL / REMEDIATION_REQUIRED**（实现 64%、真实运行证据 39%、发布就绪 34%）。
逐条去量之后：**它抓到了一个我完全没看见的真缺陷，而它的多数扣分点是在一个更早的状态上打的。**
两类都写在这里，各自带证据。

量测时刻：2026-08-05T00:13Z。`HEAD = bb8b2745`，线上 `20260805T000430Z-bb8b2745c0eb`，同一 SHA，CI 四条全绿。

## 一、它是对的，而且是最重要的一条

复审给「增量采集与数据新鲜度」14% 权重、证据只给 10%。这个方向是对的，
但**真正的问题比「漏采两天」更严重，是我自己造出来的，两边都没点破**：

22:34 的采集成功落地后，reconcile 分析了 **114,024** 条事件，而全量 union 是 **122,080** 条。
新一跑的 `normalized_batch_key` 不可能出现在 canonical MANIFEST 的 `supersedes` 里
（union 早于它），于是代码走了 else 分支，**只读了这一跑自己的批次**。
那份 MANIFEST 自己的 `loss_check` 写着：只留最新一跑会丢 10,044 条。

**「全量全时」当时已经悄悄变成了「最近一跑」，而 114,024 这个数看上去完全健康。**

修法：union 可用时两边都读，按 `event_id` 求并，批次一侧优先。
只读批次仅在完全没有 union 时保留，并在 `mode` 里说明。
实测：`114,024 + 14,471 = 127,712`，**捞回 14,471 条**。
判据断言这三个数必须相加成立——一次丢掉一侧的合并会表现为算术不成立，
而不是一个没人质疑的较小数字。

连带修掉一个它挡路的判据：这次修复让同一个 run 合法地得出了不同结论，
而不可变历史判据把它当成「运行改了口径」拒绝发布。规则本意是
**「同一次运行、同一份代码不得改变结论」**——指纹现在带上 repository_commit，
重新推导可以发布，同代码下的静默改动照样冲突；首次推导保留在
`<run_id>.json` 不被覆盖，新推导写成 `<run_id>.<commit>.json`。

## 四、我不认同的一处口径，以及理由

复审把 v0.0.0.31 判为「数据没有打通，全局数据跑通 10%」。
就「浏览器读到的是不是活数据」这个问题，实测是通的：
页面自己取到的 `/memory_atlas.json` 是本次 reconcile 现生成的 514 会话图谱，
不是发布包里烤死的快照；`generated_at` 随每次对账前移。

但复审这个方向仍然指到了真东西——**只是位置不同**：数据确实曾经不完整，
不完整的原因是上面第一条那个截断，而不是链路没打通。
**它扣对了分，理由指错了地方；而我两样都没发现。**
